## 32.0 쉬운 요약

1. **70번 실행 모두 안전**: 몸 겹침·Gazebo 접촉·칸 이탈·비상 정지·LiDAR 오탐 확정 **0**(장애물 없는 10장면에서도 오탐 후보 0). 몸 사이 최소 거리 23.9 cm 이상.
2. **성공**: 우리 방법 **50/50**, 전체 재계획 **48/50**. 전체 재계획이 실패한 2번은 모두 좁은 통로 시드 3(장애물이 **막다른 통로 끝** 1행5열) —
   PP 고정 순서로는 갇힌 로봇을 빼낼 수 없다. 저장된 재계획 입력 60개에 두 방법을 모두 돌리면(같은 입력 비교) 좁은 통로에서 **우리 50/50, 전체 45/50**.
3. **흔들림(길이 바뀐 로봇)**: 좁은 통로 평균 **3.2~3.4대 vs 3.8~4.2대**, 넓은 맵 2.8 vs 3.0대. 장애물이 지나가는 로봇이 3대라서 3대가 최소다.
4. **끝나는 시간**: 좁은 통로 기본 조건에서 끝난 시각의 합(초 단위 SOC)은 우리 방법이 평균 **6% 짧고**(352.6 vs 375.0초), 다 끝난 시간(가장 늦은 로봇)은
   거의 같다(90.8 vs 89.8초). 장면마다는 섞여 있다 — 우리가 크게 빠른 장면(시드 2·17), 같은 장면(4·13), 가장 늦은 로봇만 늦은 장면(3). 넓은 맵은 거의 같다(±3%).
   같은 입력 비교로는 계획상 SOC 차이 평균 +0.16스텝(좁은 통로), +1.2스텝(넓은 맵) — **평균적으로 비슷하고, 가끔 한쪽이 길다.** 2D와 같은 모양(32.6).
5. **계산 시간은 둘 다 0.2~1.1 ms** — 6대에서는 차이가 안 보인다(31.1에서 예상한 대로, 속도 주장의 근거는 2D).
6. **`T_wait`·`d_detect`**: `T_wait`가 길수록 늘어난 시간이 커진다(0초 → 3초 → 10초: 다 끝난 시간 +20 → +29 → +43초, 우리 방법). `T_wait` 10초에서만 HOLD가 꾸준히 나온다(평균 3.6초).
   `d_detect` 1 m는 발견이 2.4초 늦고(4.6초), 3 m는 2 m와 거의 같다(10×10칸에서는 2 m면 생기자마자 보임). 두 방법의 차이 방향은 조건이 바뀌어도 같았다.

## 32.4 같은 재계획 입력에서 두 방법 (`same_input_compare`)

3D 실행이 저장한 재계획 입력 60개(`replan_0.json`, 31.25)마다 **같은 입력**에 두 방법을 2D 파이썬으로 돌렸다(3D 연결이 맞음은 60개 모두 "3D 결과 = 2D 결과"로 확인).
끝 스텝 = 로봇마다 마지막으로 칸이 바뀐 번호(작업이 남았으면 작업 끝).

| | 좁은 통로(입력 50) | 넓은 맵(입력 10) |
|---|---|---|
| 성공 | **우리 50 / 전체 45** | 10 / 10 |
| 전체가 실패한 입력 | 5개 모두 s3(막다른 통로 끝) — 그때 우리 방법은 Tier 0(4번)·Tier 1(1번)로 풂 | — |
| 둘 다 성공: 끝 스텝 합(SOC) 우리 − 전체 | 평균 +0.16 (우리가 김 12 / 같음 22 / 짧음 11) | 평균 +1.2 (김 8 / 같음 2 / 짧음 0) |
| 둘 다 성공: 가장 늦은 끝 스텝 우리 − 전체 | 평균 +1.0 (김 10 / 같음 29 / 짧음 6) | 0 (10개 모두 같음) |
| 길이 바뀐 로봇 평균 | **3.22 / 4.09** | 2.80 / 3.00 |

- s3에서 전체 재계획이 지는 이유(31.25 HOLD 장면과 같은 구조): 장애물이 막다른 통로 끝에 생기면 통로 안의 로봇이 되돌아 나와야 하는데,
  전체 재계획은 고정 순서로 모두를 다시 계획하다가 앞 순서 로봇이 그 통로 안 목적지를 먼저 차지해 길을 막는다. 우리 방법은 그대로 둘 로봇을 먼저 고정하고(고정 먼저),
  막히면 넓히거나 비켜 세운다(Tier·구조). **장면 하나(s3)에서 나온 것**이고 시드를 더 늘려야 비율을 말할 수 있다.

## 32.6 31.23 해석 3 — "바뀐 로봇은 적은데 끝나는 시간이 길다"를 어떻게 볼까 (사용자와 정할 것)

**사실 정리**
- 31.23(7-4)의 좁은 통로 장면(s1)은 7-6에서 보면 **드문 꼬리 쪽**이다. 그 장면도 같은 입력으로 다시 보면 **계획상 SOC는 우리 방법이 작고**(40 vs 48스텝)
  **가장 늦은 한 대만** 크게 늦다(20 vs 15스텝). 31.23은 "다 끝난 시간(가장 늦은 로봇)"만 봤다.
- 7-6 10장면에서는 다 끝난 시간이 평균 거의 같고(좁은 통로 90.8 vs 89.8초), 합은 우리 방법이 짧다(352.6 vs 375.0초). 우리가 늦은 장면 1개(s3), 빠른 장면 2개(s2·s17).
- **2D 벤치마크도 같은 모양이다**(`tools/results/v7_restart/`, Windows에서 만든 CSV, 둘 다 성공한 경우):

| 2D 장면 | 지도 | 우리 SOC가 김 / 같음 / 짧음 | SOC 차이 중앙값 | 평균 | 가장 김 |
|---|---|---|---|---|---|
| 64×64 path | 좁은 통로 | 62 / 63 / 68 | 0 | +1.6 | +151스텝(+2.0%) |
| 64×64 path | 넓은 맵 | 34 / 129 / 37 | 0 | −0.7 | +48(+0.7%) |
| 64×64 standing | 좁은 통로 | 41 / 57 / 88 | 0 | −10.3 | +143(+2.7%) |
| 64×64 standing | 넓은 맵 | 21 / 116 / 63 | 0 | −3.8 | +70(+1.3%) |
| 32×32 standing | 좁은 통로 | 20 / 97 / 75 | 0 | −5.6 | +26(+11.6%) |
| 32×32 standing | 넓은 맵 | 6 / 124 / 70 | 0 | −3.3 | +34(+6.6%) |

  → **평균은 같거나 우리가 짧고, 가끔(10~32%) 우리가 길다.** 길 때 상대 차이는 큰 지도에서 2~3%, 작은 지도(로봇 적음)에서 최대 12%. 2D CSV에는 makespan 열이 없어
  "가장 늦은 로봇"은 2D에서 아직 못 봤다(9번 비교 실험 때 열을 더하면 볼 수 있음).
- 왜 생기나: 우리 방법은 Tier 0에서 A\*가 길을 찾으면 넓히지 않는다(설계). 나머지를 고정하므로 영향받은 로봇이 **길은 있지만 긴** 우회를 받을 수 있다.
  전체 재계획은 모두를 다시 짜서 그 로봇에게 짧은 길을 줄 수 있지만, 순서 때문에 다른 로봇이 늦거나(합이 길어짐) 아예 못 푸는 경우가 있다(s3).

## 32.7 정직하게 적을 것 (한계)

- **장면마다 1번**이다. 3D 실행은 매번 조금씩 달라서(s3의 확정 5.3 vs 10.5초, s17의 "장애물 있을 때 더 빠름") 한 번으로 장면별 승패를 말하면 안 된다.
