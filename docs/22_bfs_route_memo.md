# 22. BFS 길 메모장 — 같은 BFS를 한 번만 계산하기

> 2026-11-18. 작은 정리 작업. **결과는 칸마다 그대로, 같은 계산만 한 번으로 줄인다.**

## 22.0 한 줄 요약

재계획 한 번(`replan()`) 동안, 로봇마다 "다른 로봇이 없을 때의 가장 짧은 길"(BFS)을 **처음 필요할 때 한 번만 계산해서
메모장에 적어 두고**, 그 뒤로는 꺼내 쓴다. 메모장에는 **길(칸 목록)만** 적고, "그 길 위에 누가 있나"는 쓸 때마다 그 순간의
장부에서 조회한다.

## 22.1 지금 문제

BFS(`static_shortest_path`)를 부르는 곳이 세 군데이고, 같은 로봇에 대해 같은 BFS를 여러 번 계산한다.

| 부르는 곳 | 언제 | BFS 결과로 하는 일 |
|---|---|---|
| ② 도달 확인 (`replan`, 13장) | 재계획 시작, 처음 영향받은 로봇마다 | 길이 있나? 시간 안에 도착하나? (목록이 비었나, 목록 길이) |
| ③ 구조 로봇 고르기 (`shortest_path_conflicts`, 13장) | A\*가 실패할 때마다(Tier마다 또 실패하면 또) | 목록의 i번째 칸을 "출발 시각 + i"에 장부에서 조회 → 주인이 구조 후보 |
| 양보 요청 (`try_yield_requests`, 19장) | 재계획 성공 뒤, 늦어진 로봇마다 | 가장 빠른 도착(목록 길이) + 길 위에 서 있는 로봇 조회 → **같은 로봇에 BFS 2번** |

## 22.2 왜 저장해도 결과가 안 바뀌나

BFS의 입력은 **출발 칸, 목적지, 지도(벽), 새 장애물** 넷뿐이고, 다른 로봇과 장부는 보지 않는다.

- 지도: 재계획 중에 안 바뀐다.
- 새 장애물: `replan()` 한 번 안에서는 같은 목록이다.
- 출발 칸·목적지: 메모장의 **열쇠**로 쓴다. 열쇠가 같으면 입력이 같다.

그러므로 `replan()` 한 번 안에서는 열쇠가 같으면 BFS 결과가 반드시 같다. 다음 `replan()`은 새 장애물이 다를 수 있으므로
**`replan()`을 시작할 때 메모장을 비운다.**

반대로 "길 위에 누가 있나"는 저장하면 안 된다. 장부는 시도마다 다시 채워지고(`try_replan_set`의 `table_.clear()`), Tier가 오르면
구조 로봇의 옛 길이 빠지고 새 길이 들어가서 같은 칸을 조회해도 주인이 달라진다.

```
메모장에 저장 (재계획 한 번 동안 고정): W의 길 = [(3,2), (3,1), (4,1), (5,1), (5,2), (6,2)]
쓸 때마다 조회 (시도마다 다름):          Tier 0 장부 → K / Tier 1 장부 → (K는 비켰으니) 다른 로봇
```

## 22.3 설계

| 무엇 | 어떻게 |
|---|---|
| 메모장 | `PrioritizedPlanner`의 멤버 `route_memo_`: 열쇠 = (출발 칸, 목적지), 값 = 칸 목록. `mutable`(const 함수 `shortest_path_conflicts`에서도 채우므로) |
| 꺼내기 함수 | `shortest_route(from, goal, new_obstacles)`: 메모장에 있으면 그대로, 없으면 `static_shortest_path`로 계산해서 적고 돌려준다 |
| 비우기 | `replan()`(근무표 버전) 맨 앞에서 비운다 |
| 바꿀 곳 | 위 세 군데의 `static_shortest_path` 호출 → `shortest_route` |
| 계산 횟수 | `last_route_computations()`: 마지막 `replan()`에서 BFS를 실제로 계산한 횟수(테스트·확인용) |

열쇠에 새 장애물을 넣지 않는 이유: 넣으면 열쇠가 길어질 뿐이고, "재계획마다 비운다"로 충분하다. 대신 **비우기를 빠뜨리면 틀린 결과가
나온다** — 이걸 잡는 테스트를 넣는다(22.4의 2번).

## 22.4 확인 방법

1. **결과가 칸마다 같다**: 테스트 82개 + 벤치마크(v3 기준선 7개 설정, 양보 요청 켬, Tier 5 + 작업 시간 켬) 시간 열 빼고 전부 같음.
2. **새 테스트 — 메모장을 재계획마다 비우는가**: 같은 플래너로 두 번 재계획한다. 첫 번째는 장애물이 길을 완전히 끊어 실패(빈 길이 메모장에
   적힘), 두 번째는 장애물이 한 칸뿐이라 돌아가면 성공해야 한다. 비우기를 빠뜨리면 두 번째가 옛 빈 길을 보고 실패한다.
3. **새 테스트 — 정말 한 번만 계산하는가**: 13장 장면(W가 갇혀 구조 로봇 K를 부름)에서 도달 확인을 켜면, W의 BFS는 ②에서 한 번 계산되고
   ③은 꺼내 쓰므로 계산 횟수 = 1. 예전 방식이면 2.
4. **돌연변이**: (a) 비우기를 지우면 2번 테스트 실패, (b) 메모장을 안 쓰고 매번 계산하면 3번 테스트 실패.

## 22.5 기대 효과

시간은 거의 안 줄 것이다. ③은 A\*가 실패할 때만 돌고(64×64에서 400개 중 몇 개), BFS는 A\*보다 훨씬 싸다. 목적은 **같은 계산을 한 번만
하는 구조로 정리**하는 것이다. 결과(21.8 결과 표)는 그대로다.

## 22.6 결과 (2026-11-18)

- BFS를 부르는 곳이 `shortest_route` 한 곳으로 모였다(②·③·양보 요청 모두 이 함수를 거침).
- 테스트 82 → **84개** 통과. 새 테스트 2개: 13장 장면에서 BFS 계산 1번(예전 2번) / 같은 플래너로 두 번 재계획해도 옛 길을 안 씀.
- 돌연변이: (a) 비우기를 지우면 `RouteMemoIsClearedForEachReplan` 실패, (b) 메모장을 안 쓰면 `RouteMemoComputesEachRouteOnceAndKeepsResult` 실패.
- 벤치마크: v3 기준선 7개 설정 + 양보 요청(32×32, 64×64) + Tier 5·작업 시간(32×32 U[10,30], 64×64 U[30,60]) = **11개 설정 4,400 시나리오,
  시간 열 빼고 23개 열 전부 칸마다 같음.**
- 시간: 차이는 측정할 때마다 흔들리는 정도라 효과로 보지 않는다(22.5 예상대로). 구조 정리가 목적이었다.
