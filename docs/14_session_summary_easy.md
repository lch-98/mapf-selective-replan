## 먼저 읽기 — 비유로 보는 전체 이야기 (가장 쉬운 버전)

**상황.** 로봇들이 "몇 시에 어느 칸을 쓸지"를 **예약 장부**에 적어 두고 움직인다. 이미 누가 적어 둔
칸은 적을 수 없어서(거절), 로봇끼리 부딪히지 않는다. 가다가 길에 **장애물**이 생기면, 막힌 로봇만
새 길을 찾고 나머지는 원래 길 그대로 가게 하는 것이 우리 방법이다.

**문제 1 — 장부에 적는 순서가 잘못돼 있었다.** 새 길을 찾는 로봇 A가 먼저 장부를 봤는데, 원래 길로
가는 로봇 B는 아직 안 적혀 있었다. A는 "비어 있네" 하고 B가 쓸 칸을 가져가 버리고, 나중에 B의 예약은
거절된다. 게다가 한 번 거절되면 거기서 멈추기 때문에, 이런 충돌이 여러 개 있어도 **한 번에 하나씩만**
발견된다. B를 해결하면 C, C를 해결하면 D... 몇 번을 다시 해도 실패하는 경우가 많았다.

**고친 방법 1 — 원래 길로 가는 로봇들을 먼저 적는다.** 이들은 원래부터 서로 안 부딪혔으니 거절될
일이 없다. 그다음 A가 장부를 보면 전부 보이니 **처음부터 피해서** 길을 찾는다. 대가: A가 더 중요한
로봇이어도 B를 피해 돌아가야 해서, 가끔 A가 조금 늦게 도착한다.

**고친 방법 2 — "비켜 줘"라고 부탁할 로봇을 제대로 고른다.** A가 끝내 길을 못 찾으면 막고 있는
로봇에게 비켜 달라고 부탁한다. 원래는 A가 헤매다 **마주친 로봇 전부**에게 부탁했다(200대 중 199대에게
부탁한 적도 있다). 이제는 **A의 가장 짧은 길 위에 있는 로봇에게만** 부탁한다(199대 → 13대). 또
장애물이 길을 완전히 끊었으면 누구에게 부탁해도 소용없으니 바로 "못 간다"고 끝낸다.

**결과.** 64×64 맵에서 400번 중 마지막 수단 없이 푼 횟수가 207번 → 398번. 원래 길에서 바뀐 로봇
수는 평균 45대 → 3대.

**남은 문제.** (1) 길이 없을 때 포기가 너무 늦다 — "모든 칸 × 모든 시간"을 다 확인한 뒤에야 포기해서
가끔 2초 넘게 걸린다. (2) 가끔 필요 없는 로봇에게도 부탁한다 — "쉬지 않고 간다"고 가정하고 고르다 보니
잠깐 기다리면 피할 수 있는 로봇까지 부른다. (3) 중요한 로봇이 양보하는 경우가 생긴다(고친 방법 1의
대가). (4)·(5)는 정리했다 — 장애물은 **예기치 않은 장애물(Unexpected Obstacle, 나타나서 그 자리에
머무는 장애물)**로 연구 범위를 정했고(움직이는 장애물은 이후 연구), 코드 이름도 PBS에서
`PrioritizedPlanner`로 바꿨다.

## 14.0 한 장 요약

1. 우리 코드의 `PBS` 클래스는 이름만 PBS고, 실제로는 **PP(고정 우선순위 계획)**였다. 그래서
   이름을 `PrioritizedPlanner`로 바꿨다.
2. 선택적 재계획이 자주 실패하던 가장 큰 원인은 **"안 건드린 로봇"과 "다시 계획하는 로봇"을
   우선순위 순서대로 섞어서 등록하는 구조**였다.
3. 이걸 **"안 건드린 로봇 먼저 전부 등록 + 불려 온 로봇은 맨 뒤에 계획"**으로 바꿨더니,
   64×64 맵에서 안전망 없이 푼 시나리오가 **207개 → 394개**(400개 중)로 늘었다.
4. 대가도 있다. 우선순위 높은 로봇이 낮은 로봇을 피해 **혼자 돌아가느라 비용이 느는 경우**가
   생긴다. 하지만 평균 비용과 경로가 바뀐 로봇 수는 오히려 줄었다.
5. 아이디어 3도 넣었다. 특히 **"구조 후보 정교화"**는 64×64에서 안전망으로 가던 경우를 3 → 0,
   한 번에 다시 계획하는 로봇 수 최댓값을 **200 → 17대**로 줄였다. 다만 가끔 더 많이 불러 비용이

## 14.1 먼저, 기본 개념 다시 보기

### 로봇 한 대: 시공간 A\*

평범한 A\*는 (x, y) 칸 위에서 길을 찾는다. 로봇이 여러 대면 "**언제** 그 칸에 있는지"가
중요하므로, 칸에 시간을 붙인 (x, y, t) 위에서 길을 찾는다. 이것이 **시공간 A\***다.
한 스텝마다 상하좌우로 한 칸 가거나 **제자리에서 기다린다**.

### 여러 로봇: 예약 장부 + 순서대로 계획(PP)

**예약 테이블**은 "몇 시에 어느 칸을 누가 쓰는지" 적어 두는 장부다.

```
1번 로봇: A*로 길 찾기 → 장부에 예약
2번 로봇: 장부를 보고 1번이 예약한 칸·시각을 피해서 길 찾기 → 예약
3번 로봇: 1, 2번을 피해서 ...
```

이렇게 **정해진 순서대로 한 대씩** 계획하는 방법이 **PP(Prioritized Planning, 고정 우선순위
계획)**다. 앞 순서 로봇은 뒤 로봇을 신경 쓰지 않고, 뒤 로봇이 앞 로봇을 피한다.

- **도착 후 머묾(Tail)**: 로봇은 목적지에 도착하면 **끝까지 거기 머문다**고 보고, 목적지 칸을
  마지막 시각까지 예약한다.
- **등록(`register_path`)**: 경로를 장부에 적는 함수. 이미 **남이 예약한 칸이면 거절**한다.
  모든 결과 경로가 반드시 이 함수를 통과하므로, **결과에 충돌이 없다는 보장이 여기서 나온다.**

### 새 장애물이 생기면: 선택적 재계획

로봇들이 움직이는 도중에 **새 장애물**이 생겼다고 하자. 한 번 생기면 계속 그 자리에 있는
**예기치 않은 장애물(Unexpected Obstacle)**이다(떨어진 물건, 멈춰 선 설비 등). 물류 현장에서
움직이는 장애물은 곧 지나가지만, 멈춰 선 장애물은 길을 오래 막아 다른 경로를 찾아야 하게
만든다. 움직이는 장애물은 이후 연구로 미뤘다.

```
1단계  영향받은 로봇 찾기: 옛 경로가 앞으로 장애물 칸을 밟는 로봇만 "재계획 로봇"(working)
2단계  한 번 시도(Tier 0):
         - 재계획 로봇  → 지금 위치에서 A*로 새 길 → 등록
         - 나머지 로봇  → 옛 경로 그대로 등록 ("고정 로봇")
3단계  실패하면 원인 로봇을 찾아 재계획 로봇에 추가("구조 로봇") → 다시 시도 (Tier 1, 2 ...)
4단계  정해진 횟수까지 실패하면 안전망: 모든 로봇을 처음부터 다시 계획(전체 재계획)
```

**장점**: 대부분 영향받은 로봇 몇 대만 다시 계산하므로 빠르고, 다른 로봇들은 하던 대로 간다.

## 14.2 발견 1 — `PBS` 클래스는 사실 PP였다 (10장)

진짜 **PBS**(Ma 등, 2019)는 충돌이 나면 "A가 먼저 / B가 먼저" 두 갈래로 나눠서 **순서 자체를
바꿔 가며** 찾는다. 우리 코드는 `agents` 벡터 순서를 **한 번도 바꾸지 않는다.** 그래서 정확한
이름은 **PP**다.

→ 알고리즘이 틀린 건 아니다(PP로서는 정확하다). 다만 논문에서 "PBS를 썼다"고 하면 **틀린
설명**이 된다. "PP 위에 선택적 재계획을 얹었다"고 해야 한다.

**→ 해결함**: 코드 이름을 `PrioritizedPlanner`로 바꿨다(`PBSConfig` → `ReplanConfig`,
`PBSResult` → `PlanResult`, 파일 `prioritized_planner.hpp/.cpp`, 파이썬 `mapf_py.PrioritizedPlanner`).
동작은 그대로다(테스트 52개 통과). 이 문서의 아래 절들에서 "`PBS` 클래스"라고 쓴 곳은 바꾸기 전 이름이다.

## 14.3 발견 2 — 섞어서 등록하는 문제 (10장)

원래 방식은 `agents` 순서대로 돌면서 재계획 로봇이면 A\*, 고정 로봇이면 옛 경로 등록을 했다.

```
순서: [W(재계획), N(고정)]

W의 A*  : 이때 장부엔 N이 아직 없다 → N의 옛 경로를 모른 채 그 위를 지나감
N 등록  : W의 새 경로와 겹침 → 거절! → 실패 → N을 불러와 다시 시도
```

측정해 보니 첫 시도(Tier 0)가 실패한 원인의 **99% 이상이 이것**이었다.

## 14.4 구조 로봇 두 종류 (10·11장)

실패하면 "원인 로봇"을 불러온다. 불려 오는 경로가 둘이다.

| | 언제 | 불려 온 로봇의 순서 | 다시 계획하면 |
|---|---|---|---|
| **(a)** | 고정 로봇 N의 **등록이 거절**됨 | 부딪힌 상대 W보다 **뒤** | W의 새 경로를 **보고 피한다** ✅ |
| **(b)** | 재계획 로봇 W의 **A\*가 실패**함 | 막은 로봇 K는 W보다 **앞** | K가 W를 **모른 채** 먼저 계획 → 같은 길 ❌ |

(b)에서 K가 항상 앞인 이유: W가 A\*를 돌리는 순간 장부에는 W보다 앞 순서 로봇만 있으니까.

**중요한 정정**: 구조 로봇이 된다고 **우선순위가 올라가지는 않는다.** `std::find`는 "재계획
대상인가"만 확인하고, 처리 순서는 늘 원래 `agents` 순서다.

## 14.5 (a) 검증 — 정말 잘 비켜주나? (11장)

### 어떻게 쟀나

코드에 **기록만 하는 임시 장치**를 넣어서(로직은 그대로), 벤치마크와 같은 시나리오를 돌리며
"시도마다 누가 누구와 부딪혔나"를 모았다. 확인 후 장치는 지웠다.

### 결과

- **N 자신은 다음 시도에서 거의 항상 비켜 간다**: 197/197, 대규모 854/855.
  → "구조 로봇이 우선순위가 낮으면 문제없다"는 직관이 맞았다.
- 그런데 다음 시도 **전체** 성공률은 48%, 대규모 17%뿐이었다. 왜?

### 숨은 충돌

시도는 **처음 거절되는 로봇에서 바로 멈춘다.** 그래서 W가 고정 로봇 여러 대와 부딪혀도 한 번에
**하나씩만** 발견된다.

```
W의 새 경로가 N과도, M과도 부딪힌다

시도 1: N 거절 → 멈춤 (M은 검사도 안 됨)
시도 2: N 성공 → M 거절 (처음부터 있던 충돌이 이제야 보임)
시도 3: ...
```

다음 시도가 실패한 원인: **숨은 충돌 약 75%**, N의 새 경로가 다른 로봇을 막는 연쇄 약 18%,
간접 연쇄 약 6%. 처음엔 "연쇄"라고 추정했는데 **일부만 맞았다.**

## 14.6 해결 1 — 고정 로봇 먼저 등록 + 구조 로봇은 뒤에 (12장)

### 무엇을 바꿨나

한 번의 시도에서 로봇을 처리하는 **순서만** 바꿨다(처리 내용은 그대로).

```
원래(priority)   : agents 순서대로 섞어서
새 방식(fixed-first): [고정 로봇 전부: 옛 경로] → [처음 영향받은 로봇] → [구조 로봇: 불려 온 순서]
```

- 고정 로봇의 옛 경로끼리는 원래 충돌이 없고 장애물도 안 밟는다 → 먼저 등록하면 **거절이 안 생긴다.**
  → (a)와 숨은 충돌이 **통째로 사라진다.**
- 구조 로봇은 자기가 막은 로봇이 이미 목록에 있을 때 불려 오므로 **항상 그 뒤에** 계획된다.
  → (b)도 (a)처럼 "뒤에서 보고 피하는" 구조가 된다. (이것이 11장의 **아이디어 1**)

### 누가 손해를 보나 — "양날의 검"

```
원래     : W(높음)는 자기 길을 감, N(낮음)을 불러서 비키게 함
새 방식  : N의 옛 경로가 먼저 등록돼 있음 → W가 N을 피해 돌아가거나 기다림
```

즉 **우선순위 높은 W가 낮은 N을 피해 가는** 일이 생긴다. W가 돌아갈 길조차 없으면 그때 N을
불러오고(N은 W 뒤에 계획) → 원래 방식과 같은 결과가 된다.

테스트로도 확인했다: 4×3 격자 예제에서 원래 방식은 Tier 1로 K를 비키게 하지만, 새 방식은
Tier 0에서 R이 **한 스텝 기다렸다 가서** 끝난다(K는 그대로, R은 t=5 → t=6 도착).

### 결과 (64×64, 로봇 50~200대, 시나리오 400개)

| | 전체 재계획 | 원래 방식 | 새 방식 |
|---|---|---|---|
| 안전망 없이 성공 | — | 207 | **394** |
| 전체 성공 | 354 | 358 | **397** |
| 경로가 바뀐 로봇 수 평균 | 75.5 | 45.4 | **4.5** |
| 시간 중앙값 | 191 ms | 33 ms | **20 ms** |

- 양날의 검은 **실제로 있었다**: 두 방식이 모두 성공한 시나리오를 짝지어 보면, 새 방식의 비용이
  더 큰 경우가 10~18개(최대 +24)였다.
- 하지만 **더 작은 경우가 23~90개로 더 많아서** 평균 비용은 줄었다. 원래 방식은 구조 로봇을
  여러 대 부르며 그 우회 비용이 쌓이기 때문으로 보인다(추정).
- 성공 결과 3,117개를 전부 검사해 **충돌 0건**.

## 14.7 해결 2 — 아이디어 3 (13장)

### 3-1. 도달성 검사: "다른 로봇이 없어도 갈 수 있나?"

재계획을 시작할 때, 영향받은 로봇마다 **벽 + 새 장애물만 보고 BFS**로 목적지까지 가 본다.

```
못 간다 (장애물이 길을 끊음, 또는 가장 빨라도 시간 한도 안에 못 도착)
  → 누구를 불러와도, 전체 재계획을 해도 이 로봇은 절대 못 간다
  → Tier와 안전망을 건너뛰고 바로 "실패"
```

- **결과를 바꾸지 않는다**: 어차피 실패할 경우만 일찍 끝낸다. 실험에서 켠 것과 끈 것의
  성공/실패·비용·Tier가 **완전히 같음**을 확인했다.
- 효과는 **시간**뿐이다. 그런데 이번 벤치마크에는 "다른 로봇이 없어도 못 가는" 경우가 **하나도
  없어서** 시간 이득도 측정되지 않았다(벤치마크가 목적지·출발지를 막는 장애물을 일부러 피하기
  때문으로 보인다). GUI처럼 사람이 아무 데나 장애물을 놓는 상황에서 쓸모가 있다.

### 3-2. 구조 후보 정교화: "최단 경로와 부딪히는 로봇만"

원래는 A\*가 실패하면 **탐색 중 한 번이라도 막혀 본 모든 칸의 주인**을 불렀다. A\*는 실패하기까지
갈 수 있는 곳을 **전부** 뒤지므로, 길과 상관없는 먼 로봇까지 끌려왔다(12장: 194대!).

새 방식은 **"다른 로봇이 없을 때의 최단 경로"를 쉬지 않고 따라간다고 보고**, 그 경로와 실제로
부딪히는 로봇만 부른다(칸 충돌, 자리 맞바꾸기, 도착 후 목적지를 차지한 로봇).

```
  y=0:  # # # # . # # #      K: (4,1)에 머묾  ← W의 길을 막음
  y=1:  Z # # . K . # #      Z: (0,1)에 머묾  ← W의 길과 무관
  y=2:  . . . W X . . .      X: 새 장애물, W는 오른쪽 (6,2)로 가야 함

원래 방식: W의 A*가 헤매다 Z에게도 막혀 봄 → K와 Z 둘 다 불러옴
새 방식  : 최단 경로 (3,1)→(4,1)→(5,1)... 과 부딪히는 건 K뿐 → K만 불러옴
```

부딪히는 로봇이 전부 이미 재계획 중이면(새로 부를 로봇이 없으면) 원래 방식으로 돌아간다.

### 결과

기본 맵(32×32, 400개):

- 3-2를 켜면 안전망 없이 성공 399 → **400**. 한 번에 다시 계획한 로봇 수의 최댓값이 **40 → 10**.
- 하지만 **항상 좋지는 않았다.** 몇몇 시나리오에서는 오히려 더 많이 불렀다(2 → 6대, 비용 +45).
  "쉬지 않고 가는" 일정으로만 부딪힘을 보기 때문에, **잠깐 기다리면 피할 수 있는 로봇까지
  원인으로 잡는 것**으로 보인다(추정).
- 느린 경우(약 300 ms)는 그대로였다. 시간이 **A\*가 실패하며 전부 뒤지는 데** 쓰이기 때문이고,
  아이디어 3은 그 부분을 줄이지 않는다.

대규모 맵(64×64, 400개, Tier 최대 1) — 여기서 3-2의 효과가 뚜렷했다:

| | fixed-first | + 도달성 검사 + 3-2 |
|---|---|---|
| 안전망 없이 성공 | 394 | **398** |
| 안전망 / 실패 | 3 / 3 | **0 / 2** |
| 한 번에 다시 계획한 로봇 수 최댓값 | 200 | **17** |
| 추가 비용 평균 | 10.6 | **9.2** |
| 바뀐 로봇 수 평균 | 4.5 | **3.3** |
| 시간 평균 | 84 ms | **64 ms** |

- 원래 방식은 로봇이 많으면 A\*가 헤매며 **거의 모든 로봇**을 불러왔다(200대 중 199대!). 3-2는
  길 위의 로봇만 부른다.
- 결과가 바뀐 11개 시나리오 중 **좋아짐 6, 섞임 2, 나빠짐 3**. 좋아진 건 "100~200대를 끌어오던"
  극단적인 경우고, 나빠진 건 "2~3대 → 3~9대" 정도의 작은 차이다.
- 아무도 못 풀던 시나리오 1개(Tier 5 설정이면 2개)를 새로 풀었다.

## 14.8 아직 남은 문제

| 문제 | 왜 생기나 | 가능한 해결 |
|---|---|---|
| A\* 실패가 느리다(수백 ms) | 길이 없으면 (칸 수 × 시간)을 전부 뒤져야 끝난다 | 실제 최단거리 휴리스틱(갈 수 없는 칸을 미리 가지치기), SIPP |
| 3-2가 가끔 더 많이 부른다 | "쉬지 않는 일정"만 보고 부딪힘을 판단 | 대기를 허용한 경로로 판단하거나, 두 방법 중 적은 쪽 선택 |
| 우선순위 높은 로봇이 돌아간다 | 고정 로봇 먼저 등록의 본질적 대가 | 비용이 크게 늘 때만 낮은 로봇을 부르는 규칙 |
| 비교 기준이 약하다 | 전체 재계획도 순서 하나짜리 PP | 논문에서 명시, 필요하면 더 강한 기준 추가 |
| 움직이는 장애물은 다루지 않는다 | 범위 결정: 나타나서 머무는 **예기치 않은 장애물**만 대상(물류 현장에서 움직이는 장애물은 곧 지나감) | 이후 연구(09장) |

## 14.10 용어집

| 용어 | 뜻 |
|---|---|
| 시공간 A\* | (x, y, t) 위에서 찾는 A\*. 기다리기도 한 동작 |
| 예약 테이블 | "몇 시에 어느 칸을 누가 쓰는지" 적는 장부 |
| PP | 정해진 순서대로 한 대씩 계획하는 방법(고정 우선순위). 코드에서는 `PrioritizedPlanner` |
| PBS | 순서 자체를 바꿔 가며 찾는 방법. 우리 코드는 이게 **아님**(예전 클래스 이름이었지만 바꿈) |
| 예기치 않은 장애물 (Unexpected Obstacle) | 실행 도중 계획에 없이 나타나 그 자리에 머무는 장애물. 이 연구가 다루는 장애물 |
| Tail (도착 후 머묾) | 도착한 로봇이 목적지를 끝까지 차지한다고 보고 예약하는 것 |
| 등록 (`register_path`) | 경로를 장부에 적기. 남의 예약과 겹치면 거절 → 안전 보장의 핵심 |
| 재계획 로봇 (working) | 이번 시도에서 A\*로 새로 길을 찾는 로봇 |
| 고정 로봇 | 옛 경로를 그대로 쓰는 로봇 |
| 구조 로봇 | 실패의 원인이라 불려 와서 재계획 로봇이 된 로봇 |
| Tier | 몇 번째 시도인지. Tier 0 = 영향받은 로봇만, Tier 1+ = 구조 로봇 추가 |
| 안전망 | 모두 실패하면 전체를 다시 계획하는 마지막 수단 |
| 숨은 충돌 | 원래 있던 충돌이, 시도가 첫 실패에서 멈추는 탓에 한 번에 하나씩만 드러나는 것 |
| 경로 비용 합 | 모든 로봇의 도착 시각을 더한 값. 작을수록 좋다 |
| 바뀐 로봇 수 | 재계획 후 움직임이 원래와 달라진 로봇 수. 작을수록 "덜 건드림" |
| BFS | 시간 없이 칸만 보는 가장 단순한 최단 경로 탐색 |
| 도달성 | 다른 로봇이 없어도 목적지까지 갈 수 있는가 |
