# 23. 새 실험 2개 — 계산 시간의 손해, 서 있는 로봇이 길목에 있는 장면

> 2026-11-18. 일정 6번(비교 기준) 전에 하는 실험. 21장 21.8에서 나온 두 가지 숙제에 답한다.
> (1) "선택적 재계획은 빠르기만 하고 품질은 같다 — 빠른 게 현장에서 의미가 있나?"
> (2) "작업 시간을 켜도 결과가 거의 안 바뀐다 — 작업 시간이 중요한 장면은 어떻게 만드나?"

## 23.1 실험 ① — 계산 시간을 로봇 손해로 바꾸기

### 지금 벤치마크의 빈틈

지금은 재계획이 3초 걸려도 0.03초 걸려도 "경로 품질"만 비교한다. 실제 로봇은 계산이 끝날 때까지 새 계획이 없으므로
**기다려야** 한다. 그 기다림이 손해다.

### 규칙: "계산하는 동안 모두 멈춤" (두 방법에 똑같이)

- 한 스텝(한 칸 이동)에 실제 시간 Δ초가 걸린다고 둔다.
- 재계획에 c초가 걸리면, 모든 로봇이 k 스텝(아래 정의) 동안 제자리에서 기다린 뒤 새 계획을 시작한다.
- 모두 똑같이 k 스텝 멈추면 새 계획을 k 스텝 뒤로 미룬 것과 같아서 **충돌이 생기지 않는다**(장애물은 그대로 있으므로).
- 손해: 아직 목적지에 도착하지 않은 로봇(`moving_at_t`)마다 도착이 k 스텝 늦어진다 → **k × moving_at_t 스텝**.

**k의 정의(최종)**: 장애물을 본 순간부터 다음 스텝이 시작되기 전까지(Δ초) 계산이 끝나면 로봇은 멈추지 않는다.
그 뒤로는 Δ초마다 한 스텝씩 멈춘다. 그래서 `k = max(0, ⌈c / Δ⌉ - 1)`.

| 계산 시간 c | Δ = 0.5초일 때 k |
|---|---|
| 0.03초 | 0 |
| 0.5초 | 0 |
| 0.6초 | 1 |
| 3.1초 | 6 |

### 총손해 = 계획의 질 + 계산 시간

`총 늦어짐 = (재계획 결과의 도착 시각 합 − 처음 계획의 도착 시각 합) + k × moving_at_t`

앞의 항은 지금까지 잰 "경로 품질" 차이, 뒤의 항이 새로 넣는 "계산 시간 손해"다.

### Δ는 얼마로?

| 로봇 | 속도 | 한 칸 | Δ |
|---|---|---|---|
| 창고 로봇(일반) | 약 1~1.5 m/s | 약 1 m | 약 0.7~1초 |
| TurtleBot3 Burger(8번 실험) | 최대 0.22 m/s | 0.3~0.5 m(정해야 함) | 약 1.4~2.3초 |

그래서 Δ = **0.25, 0.5, 1, 2초** 네 값으로 보고, 결과가 Δ에 따라 어떻게 바뀌는지 보여 준다.

### 공정성: 시간 측정

지금 벤치마크는 모든 CPU 코어로 동시에 돌려서 시간이 서로 방해받는다. 이 실험은 **`--threads 1`(한 번에 하나씩)**로 잰다.
결과 열은 스레드 수와 상관없이 같아야 한다(확인 항목).

### 한계(논문에 적을 것)

"모두 멈춤"은 가장 단순하고 보수적인 실행 규칙이다. 선택적 재계획은 다시 계획하지 않는 로봇의 길이 안 바뀌므로, 그 로봇들은 계산 중에도
계속 움직이게 할 수도 있다(우리에게 더 유리). 이번에는 두 방법에 같은 규칙을 써서 비교만 공정하게 한다.

## 23.2 실험 ② — 서 있는 로봇이 우회로에 있는 장면

### 왜 지금은 작업 시간이 결과를 안 바꾸나(21.8)

작업 시간이 결과를 바꾸는 건 "목적지에 서 있는 로봇이 비켜야 하는데, 작업 중이라 못 비키는" 경우뿐이다. 지금 장애물은
움직이는 로봇의 경로 중간에 무작위로 놓여서, 막힌 로봇이 돌아갈 길에 서 있는 로봇이 거의 없다.

### 새 장애물 모드 `--obstacle-mode standing`

장애물 후보(지금과 같은 규칙으로 고른 "누군가 지나갈 칸") 중에서 다음을 만족하는 것만 쓴다.

> 막힌 로봇 W가, 장애물을 피해 가는 **가장 짧은 우회로**(다른 로봇 무시, BFS) 위에
> **장애물이 생기는 순간 이미 자기 목적지에 도착해 서 있는 로봇 R**의 칸이 있다.

즉 "돌아가려는 길목에 누군가 서 있는" 장면이다. R이 작업 중이면 비킬 수 없고, 주차 중이면 비킬 수 있다 → 작업 시간이 결과를 바꿀 수 있는 장면.

- 후보는 무작위 순서로 하나씩 확인하고 처음 맞는 것을 쓴다(맞는 후보 중 무작위로 고른 것과 같다).
- 맞는 후보가 없으면 그 시나리오를 버리고 다시 뽑는다(지금 규칙과 같은 방식).
- 기본값 `--obstacle-mode path`는 지금과 완전히 같아야 한다(확인 항목).

### 보는 것

작업 시간 0 / U[1,10] / U[30,60]에서 같은 standing 시나리오의 결과 차이: 성공, 안전망 없이 성공, 늦어진 로봇, 목적지 밖 시간, 구조 로봇 수.
그리고 지금 모드(path)와 비교해 "결과가 바뀐 시나리오 비율"이 늘었는지.

## 23.3 벤치마크에 더하는 것

| 무엇 | 내용 |
|---|---|
| 열 `moving_at_t` | 장애물 순간 아직 목적지에 도착 안 한 로봇 수(처음 계획 기준). 실험 ①의 손해 계산에 쓴다 |
| `--threads N` | 동시에 돌릴 스레드 수(기본: CPU 수). 결과 열은 같고 시간만 깨끗해진다 |
| `--obstacle-mode path\|standing` | 장애물 고르는 방식(기본 path = 지금과 같음) |

## 23.4 확인 항목

1. 옵션 없이 돌리면 v3 기준선과 칸마다 같다(새 열만 추가).
2. `--threads 1`과 기본의 결과 열이 칸마다 같다.
3. standing 조건이 실제로 장면을 바꾸는지: 구조 로봇을 부른 시나리오, 작업 시간 때문에 결과가 바뀐 시나리오가 path 모드보다 늘어야 한다.
   (처음에는 "시나리오마다 조건을 따로 검사"하려 했으나 CSV에 장애물 위치가 없어, 결과 분포로 확인하는 방식으로 바꿨다.)
4. 돌연변이: standing 조건 검사를 일부러 끄면(항상 "맞음") 3번의 숫자가 path 모드 수준으로 돌아가야 한다.

## 23.5 결과 (2026-11-18)

### 확인

- 옵션 없이: v3 기준선 7개 설정 2,800 시나리오, 공통 23개 열 칸마다 같음. `--threads 1`도 결과 열 같음.
- standing 돌연변이(조건을 항상 "맞음"으로): 32×32에서 작업 U[30,60] 때문에 결과가 바뀐 시나리오 **155 → 15개**, 구조 로봇을 부른 시나리오
  **18 → 1개**, 평균 장애물 시각 21.6 → 13.4 — path 모드 수준으로 돌아감. 되돌린 빌드는 저장한 결과와 칸마다 같음.

### 발견 0: 예전 시간 수치는 동시 실행 때문에 부풀려져 있었다

모든 코어로 동시에 돌리면 계산끼리 방해한다. 한 번에 하나씩(`--threads 1`) 재면 (64×64, 우리 방법 설정의 행):

| 로봇 수 | 전체 재계획 중앙값 / 느린 5% / 최대 | 우리 방법 중앙값 / 느린 5% / 최대 | 배수(중앙값) | (참고) 동시 실행 때 중앙값 전체 / 우리 |
|---|---|---|---|---|
| 50 | 17 / 119 / 489 ms | 2.1 / 7 / 16 ms | 8× | 51 / 5.0 ms |
| 100 | 82 / 295 / 796 ms | 4.6 / 13 / 25 ms | 18× | 208 / 12.3 ms |
| 150 | 166 / 598 / 1,118 ms | 8.7 / 54 / 257 ms | 19× | 412 / 24.3 ms |
| 200 | 251 / 1,097 / 1,490 ms | 12.2 / 292 / 849 ms | 21× | 639 / 33.1 ms |

**배수는 그대로, 절대 시간은 약 40%.** 논문용 시간은 `--threads 1`로 잰다(20장 원칙에 추가).

### 실험 ① 결과: 계산 시간을 손해로 넣으면

로봇당 총 늦어짐(경로로 늦어진 것 + 계산 동안 멈춘 것, 스텝), 64×64:

| 로봇 수 | Δ = 0.25초 (전체 / 우리 / 원래 방식) | Δ = 0.5초 | Δ = 1초 | Δ = 2초 |
|---|---|---|---|---|
| 50 | 0.18 / **0.11** | 0.17 / 0.11 | 0.17 / 0.11 | 0.17 / 0.11 |
| 100 | 0.17 / **0.08** | 0.11 / 0.08 | 0.10 / 0.08 | 0.10 / 0.08 |
| 150 | 0.50 / **0.08** / 0.33 | 0.16 / 0.07 / 0.11 | 0.06 / 0.07 | 0.05 / 0.07 |
| 200 | 1.08 / **0.16** / 0.76 | 0.46 / **0.12** / 0.35 | 0.14 / 0.11 / 0.13 | 0.09 / 0.11 / 0.10 |

(원래 방식은 같은 시나리오의 별도 실행. 150·200대만 표시.)

| 64×64, 200대 | Δ = 0.25초 | 0.5초 | 1초 | 2초 |
|---|---|---|---|---|
| 전체 재계획 때문에 로봇이 멈춘 시나리오 | 51% | 32% | 5% | 0% |
| 우리 방법 때문에 멈춘 시나리오 | 3% | 1% | 0% | 0% |

해석:
- **빠른 로봇(Δ ≤ 0.5초) + 로봇 150대 이상이면 차이가 크다**: 200대 Δ=0.25초에서 로봇당 늦어짐 1.08 → 0.16(약 7분의 1).
  원래 방식(0.76)은 안전망으로 자주 넘어가서 이 이점을 대부분 잃는다.
- **Δ ≥ 1초면 차이가 거의 없다.** 전체 재계획도 대부분 1초 안에 끝나기 때문이다. 이 규모에서는 계산 시간이 손해로 거의 안 이어진다.
- **경로 품질만 보면** 50·100대에서는 우리가 낫고(0.11 vs 0.17), 150·200대에서는 우리가 조금 나쁘다(0.07 vs 0.05, 0.11 vs 0.09).
- 32×32(40대 이하)는 아무도 멈추지 않는다 — 차이 없음.
- **의미**: "빠름"이 현장 이득이 되려면 **더 큰 규모**(로봇 수백~수천 대)나 **빠른 로봇**이 필요하다. TurtleBot3(Δ ≈ 2초, 로봇 몇 대)에서는
  속도 이점이 드러나지 않는다 → 8번(Sim2Real)은 "같은 알고리즘이 실제 로봇에서 충돌 없이 돈다"를 보이는 데 집중해야 한다.

### 실험 ② 결과: 서 있는 로봇이 우회로에 있는 장면

400 시나리오, 우리 방법 설정. "결과가 바뀐 시나리오" = 같은 시나리오에서 작업 시간 0과 결과 열이 하나라도 다른 것.

| | 작업 중 로봇 비율 (U[30,60]) | 작업 U[30,60]로 결과 바뀐 시나리오 (전체 / 우리) | 구조 로봇 부른 시나리오 (작업 0) |
|---|---|---|---|
| 32×32 path(기존) | 24.7% | 7 / 1 | 3 |
| 32×32 **standing** | 45.7% | **148 / 17** | 18 |
| 64×64 path(기존) | 20.2% | 28 / 4 | 13 |
| 64×64 **standing** | 37.0% | **115 / 18** | 19 |

- 시나리오(배치·장애물·시각)는 작업 시간과 상관없이 같음(확인).
- **전체 재계획은 작업 시간에 크게 흔들린다**(최대 37%의 시나리오에서 결과가 바뀜). 서 있는 로봇까지 전부 다시 계획하는데, 주차 중이면 옮길 수 있고
  작업 중이면 못 옮기기 때문이다.
- **우리 방법은 적게 바뀐다**(4~5%). 서 있는 로봇을 대개 건드리지 않고 돌아가기 때문이다. 하지만 **바뀐 경우에는 비용이 크다**:
  목적지 밖 시간이 평균 +38(32×32)·+23(64×64), 최대 +60. 작업 중인 로봇이 비킬 수 없어서, 막힌 로봇이 작업이 끝날 때까지 기다리거나
  크게 돌아가야 하기 때문이다.
- 이건 결함이 아니라 **현실을 반영한 비용**이다. 작업 시간을 0으로 두면 작업 중인 로봇도 즉시 비킬 수 있다고 가정해서, 이런 장면에서
  **실제로는 실행할 수 없는 낙관적인 계획**을 낸다. 즉 작업 시간을 모델에 넣는 것이 의미 있는 장면이 standing 모드에서 처음 드러났다.
- 전체 평균으로는 두 방법이 비슷하다(64×64 U[30,60] 목적지 밖 1,621 vs 1,622, 늦어진 로봇 2.47 vs 1.56).
