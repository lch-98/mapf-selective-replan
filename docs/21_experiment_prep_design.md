## 21.1 지금 어떤 상태인가 (코드를 읽고 확인한 것)

1. **벤치마크(`tools/benchmark.cpp`)는 근무표 없는 예전 `replan`/`full_replan`을 부른다.** 이 버전은 작업 시간이 전부 0일 때만
   허용된다(17장). 그래서 작업 시간을 켜려면 먼저 근무표 버전으로 바꿔야 한다 → 5-2.
2. **GUI 오른쪽 패널은 사실상 "원래 방식"이다.** `PrioritizedPlanner(self.game_map)`로 기본 설정을 쓰는데, 기본 설정은
   `order = 우선순위 순`, 도달 확인 끔, 구조 = 막힌 칸이다. 파이썬에서 `ReplanConfig`의 `max_escalation_tiers` 하나만 바꿀 수
   있어서 우리 방법을 고를 방법이 없었다 → 5-1, 5-4.
3. **GUI도 근무표 없는 예전 버전을 부르고, 로봇은 모두 작업 시간 0으로 만든다.** "작업 중" 상태가 화면에 나올 일이 없다 → 5-4.
4. GUI의 "기다리는 로봇" 표시(`waiting_agent_ids`)는 "이번 스텝에 제자리, 나중에 다시 움직임"으로 판정한다. 작업 시간을 켜면
   **작업 중이었다가 나중에 구조되어 비키는 로봇**도 여기에 걸려 "양보하며 기다림"으로 잘못 보인다 → 5-4에서 작업 중 로봇을 뺀다.

## 21.2 벤치마크의 작업 시간 옵션 (5-3)

### 분포: 정수 균등 분포 `U[LO, HI]` (추천)

로봇마다 따로 `LO` 이상 `HI` 이하의 정수 하나를 같은 확률로 뽑아 `service_time`으로 준다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **A. 정수 균등 `U[LO, HI]` (추천)** | 작업마다 길이가 다른 현장과 비슷. `LO = HI`로 두면 B(고정값)도 된다 | 실제 현장 분포와 같다는 근거는 없음 |
| B. 모두 같은 값 S | 가장 단순 | 모든 로봇의 작업 길이가 같아 "작업 끝 시각"이 도착 시각 차이로만 퍼짐 |
| C. 일부 로봇만 작업(비율 p) | 통과만 하는 로봇과 섞인 현장 | 스위치가 하나 더 늘어남. A에서 `LO = 0`이면 비슷한 효과 |
| D. 긴 꼬리 분포(기하 분포 등) | 가끔 아주 긴 작업 | 지금 단계에선 과함. 필요하면 나중에 |

명령줄: `--service LO HI` (기본: 옵션 없음 = 전부 0, 지금과 똑같음).

### 핵심 설계: 작업 시간은 **따로 뽑는 난수**로

지금 벤치마크는 task마다 난수 생성기 하나(`rng`)로 로봇 배치와 장애물을 뽑는다. 작업 시간을 **같은 `rng`에서** 뽑으면,
작업 시간을 켜는 순간 난수 순서가 밀려서 **로봇 배치와 장애물까지 전부 달라진다.** 그러면 "작업 시간을 켰더니 결과가 달라졌다"가
작업 시간 때문인지, 시나리오가 바뀐 탓인지 알 수 없다(20장 원칙 5).

그래서 작업 시간은 task 씨앗에서 만든 **별도의 난수 생성기**(`std::seed_seq{task.seed, 1}`)로 뽑는다.

```
같은 task 씨앗
 ├─ rng          → 로봇 출발·목적지, 장애물, 장애물 시각   (작업 시간을 켜든 끄든 똑같이 흘러감)
 └─ service_rng  → 로봇마다 작업 시간                        (작업 시간을 켤 때만 씀)
```

**왜 이것만으로 시나리오가 같아지나** (예상, 실험으로 확인할 것):
- 처음 계획(`plan`)의 성공 여부: 작업 시간이 있어도 "도착 후 목적지가 끝까지 비어 있어야 한다"는 A\*의 도착 조건은 같다.
  경로 끝에 목적지 칸이 작업 시간만큼 더 붙을 뿐이다. 다르게 될 수 있는 건 `도착 + 작업 > max_timestep(256)`인 경우뿐인데,
  64×64 평균 도착이 약 50스텝이라 `HI`를 100 이하로 두면 생기지 않는다.
- 장애물 위치: 장애물 후보는 "누구의 목적지도 아닌 경로 칸"이라, 경로 끝에 붙은 목적지 칸은 후보에 안 들어간다.
- 그러므로 `plan_attempts`, `initial_soc`, `current_time`이 작업 시간을 켜든 끄든 **칸마다 같아야 한다.** 이걸 5-3의 확인 기준으로 쓴다.

### 실험 수준은 예비 실험으로 정한다

"작업 시간이 길다/짧다"는 **장애물이 나타난 순간 작업 중인 로봇이 얼마나 있나**(`working_at_t`)로 느껴진다. 이 값은 이동 시간
(32×32 평균 도착 약 23스텝, 64×64 약 50스텝)과 장애물 시각에 따라 달라지므로, 미리 숫자를 정하지 않고 예비 실험으로 정한다.

- 후보: `0`, `U[1,10]`, `U[10,30]`, `U[30,60]` × 두 크기(기본, `--large`).
- 각각에서 `working_at_t / num_agents`의 평균을 보고, "작업 중 로봇이 거의 없음 / 조금 / 많음" 세 수준이 나오도록 2~3개를 고른다.
- 고른 수준과 이유를 이 장 21.8에 적는다.

### 결과 지표에서 조심할 것

- 경로 비용 합(`*_soc`)은 지금처럼 **도착 시각의 합**이다(경로 끝에서 목적지에 머문 구간을 빼고 셈). 작업 시간이 있어도
  작업 구간은 목적지에 머문 구간이라 자동으로 빠진다. "작업 끝 시각의 합"은 도착 시각 합 + (작업 시간 합, 상수)라서
  방법끼리 비교할 때는 같은 정보다.
- 목적지 밖 시간(`*_away`)은 작업 중엔 목적지에 있으므로 늘지 않는다. 주차 중 구조되어 비키면 그만큼 는다 — 의도한 대로다.

## 21.3 벤치마크 새 열 (5-2)

20장 원칙 4에 맞춰, CSV **맨 뒤에** 열 5개를 붙인다(앞의 열 순서는 그대로 → 예전 결과와 열 이름으로 비교 가능).

| 열 | 뜻 | 계산 |
|---|---|---|
| `current_time` | 장애물이 나타난 시각 | 이미 계산하고 있음, 기록만 |
| `working_at_t` | 그 시각에 작업 중이던 로봇 수 | `task_state_at(근무표[id], current_time) == 작업 중`인 로봇 수 |
| `full_replan_delayed` | 전체 재계획에서 원래보다 늦게 (다시) 도착한 로봇 수 | `arrival_time(새 경로) > arrival_time(처음 경로)` |
| `selective_delayed` | 선택적 재계획에서 같은 것 | 〃 |
| `selective_rescued` | 구조 로봇 수 | `rescued_ids.size()` |

"늦게 (다시) 도착"의 뜻: 주차 중에 구조되어 비켰다가 돌아온 로봇도 마지막으로 목적지에 들어온 시각이 늦어지므로 "늦어짐"으로 센다.
작업은 이미 끝났지만, 그 로봇이 다음 일을 받을 수 있는 시각이 늦어진 것이므로 현장에서 보면 피해가 맞다.

### 5-2의 확인

1. **작업 시간 0에서 결과가 같다**: 근무표 버전으로 바꾼 뒤, 기준선(`tools/results/v2_tiebreak/`)과 **공통 열을 칸마다** 비교
   (시간 열 제외). 2-2·양보 끔이 v2와 같다는 건 이미 확인했으므로 v2가 기준선이다.
2. **새 열이 말이 되는지 검사**(모든 행):
   - 작업 시간 0이면 `working_at_t == 0`.
   - `selective_delayed <= selective_replanned` — 다시 계획하지 않은 로봇은 경로가 그대로라 늦어질 수 없다.
   - `selective_rescued <= selective_replanned`.
3. **돌연변이 확인**: `delayed`를 `>=`로 일부러 틀리게 바꾸면 2번 검사가 깨지는지 본다(모든 로봇이 "늦어짐"으로 잡혀 `delayed > replanned`).

## 21.5 GUI (5-4)

### 바꿀 것

| 무엇 | 어떻게 |
|---|---|
| 명령줄 | `--service LO HI`(기본 0 0), `--method ours\|legacy`(오른쪽 패널의 방법) |
| 로봇 만들기 | `make_random_agents`에 작업 시간을 넣는다. 벤치마크처럼 별도 난수로 뽑아서, `--seed`가 같으면 작업 시간을 켜든 끄든 로봇 배치가 같게 |
| 근무표 | 패널마다 `schedule`을 들고 다닌다. 처음은 `schedule_from_plan`. 재계획 후: 오른쪽은 `result.schedule`, 왼쪽(전체 재계획)은 `update_schedule(agents, 이전 근무표, 결과, 시각)` |
| 재계획 호출 | 근무표 버전 `replan`/`full_replan` |
| 작업 중 표시 | 로봇 원 안에 **남은 작업 스텝 수**를 흰 숫자로. 색이 로봇마다 달라 색으로는 구분이 어려우므로 글자로 구분한다 |
| 주차 중 표시 | 따로 표시하지 않음(지금 모습 그대로). 작업 시간 0이면 도착한 로봇은 전부 주차 중이라, 표시하면 화면이 지저분해진다 |
| 기다림 표시 | `waiting_agent_ids`에서 **지금 작업 중인 로봇은 뺀다**(21.1의 4번) |
| 아래 통계 | "작업 중 N대" 한 줄 추가. 오른쪽 머리글에 방법 이름(우리 방법 / 원래 방식) |

`--method ours`의 설정 = 벤치마크의 우리 방법과 같다: `order = FIXED_FIRST`, `check_reachability = True`, `rescue_selection = PATH`
(양보 요청은 끔, 기본값과 같음).

### 실패했을 때

지금 GUI는 한쪽이라도 재계획에 실패하면 조작을 멈추고 R(새로 시작)만 받는다(`is_failed`). 그래서 "실패 후 멈춰 선 경로에 근무표를
어떻게 맞추나"는 생각할 필요가 없다. 실패한 패널의 근무표는 이전 것을 그대로 둔다.

### 확인 방법

GUI는 자동 테스트가 없으므로:
1. `--service 0 0`이면 예전과 같은 화면(같은 씨앗으로 띄워 눈으로 비교 + 장애물 하나 놓고 통계 숫자 비교).
2. `--service 5 10`으로 띄워서 로봇이 도착하면 숫자가 줄어들며 멈춰 있고, 0이 되면 숫자가 사라지는지.
3. 작업 중인 로봇 옆에 장애물을 놓아 구조가 필요한 상황을 만들고, 그 로봇이 **작업이 끝난 뒤에** 비키는지(17장 규칙).
4. 스크린샷을 남겨 문서에 붙인다.

## 21.6 (선택) 동점 규칙 스위치 (5-5)

20장 원칙 3의 민감도 실험에 필요하다. `AStarConfig`에 동점 규칙을 고르는 값을 넣는다.

| 값 | 동점일 때 |
|---|---|
| `kLargerG`(기본, 지금과 같음) | g 큰 쪽 → 먼저 넣은 쪽 |
| `kSmallerG` | g 작은 쪽 → 먼저 넣은 쪽 |
| `kRandom` + 씨앗 | g 큰 쪽 → 씨앗으로 정한 무작위 번호 순 |

- 기본값에서 결과가 칸마다 같아야 한다. 다른 값에서는 결과가 달라져야 한다(돌연변이 확인 겸).
- 벤치마크 옵션 `--tie-break larger-g|smaller-g|random:SEED`.
- 지금 넣을지, 일정 9번 직전에 넣을지는 결정 필요(21.7 질문 3).
