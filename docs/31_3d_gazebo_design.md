## 31.0 다섯 줄 요약

1. **알고리즘(코어)은 한 줄도 안 고친다.** ROS2 노드가 지금 C++ 코어의 `replan()`, `full_replan()`을 그대로 부른다.
2. 로봇은 **각자 다른 선속도·각속도로, 연속 시간에** 움직인다. 서로 부딪히지 않게 하는 것은 **ADG**(Action Dependency Graph, Hönig 외 2019)다.
   ADG는 계획에서 **"칸을 쓰는 순서"만 뽑아 약속으로 지키게** 해서, 길이 겹치는 로봇끼리만 겹치는 칸에서 기다린다.
   단 **ADG는 물리 충돌 검사기가 아니다.** 안전은 계획·순서·몸의 세 겹으로 보고, 몸이 실제로 안 겹치는지는 따로 검사한다(31.4).
3. 장애물은 Gazebo에 상자를 갑자기 만들어 생긴다. 로봇은 **발견(거리 `d_detect`) → 앞에서 멈춤 → `T_wait`초 동안 지켜봄 → 그래도 있으면 확정 → 재계획**한다.
4. 재계획할 때는 **"지금 모습 = 새 0번"**으로 남은 길에 번호를 다시 붙인다. 이때 **ADG 약속을 지키며 한 스텝씩 흉내 내서** 붙여야 부딪히지 않는다(31.6).
   그다음은 2D와 똑같이 `replan(..., current_time = 0)`이다.
5. 실제 로봇은 **6대**라서 시뮬레이션도 **6대가 기본**이다. 비교는 **전체 재계획과만** 한다. 6대에서는 계산 시간 차이(ms)가 거의 안 보이고,
   3D가 보여 주는 것은 "실제처럼 속도가 제각각이어도 충돌 0" + "멈추거나 길을 바꾸는 로봇이 적어서 전체 지연이 적다"이다.

## 31.1 3D에서 보여 주려는 것 / 보여 줄 수 없는 것

> **사용자 관점(2026-11-25)**: 3D를 하는 가장 큰 이유는 **우리 알고리즘이 물리 세계에서 잘 작동하는지** 확인하는 것이다.
> 논문 기여의 중심은 재계획 알고리즘(2D에서 보인 계산 시간·성공률)이고, 3D 검증과 "다시 계획하는 로봇이 적음"을 기여에 어떻게 넣을지는 나중에 26장과 함께 정한다.

| | 내용 |
|---|---|
| **보여 줄 것** | ① 2D에서 만든 계획·재계획이 **로봇마다 속도·회전 속도·작업 시간이 다른** 물리 시뮬레이션에서도 충돌 없이 끝까지 실행된다. ② 장애물이 나타나면 **영향받은 로봇만** 멈추거나 길을 바꾸고 나머지는 그대로 간다(전체 재계획은 더 많은 로봇의 길이 바뀜). ③ 작업 중인 로봇은 실제로도 안 움직인다. ④ 장애물 등장 → 발견 → 확정 → 재계획 → 다시 출발까지 걸린 **실제 시간(초)**과, 그 때문에 늘어난 전체 작업 시간. |
| **보여 줄 수 없는 것(정직하게 적을 것)** | Gazebo와 실제 로봇은 6~12대 규모라서 **200~500대에서 나온 21~137배 계산 속도 차이는 3D에서 재현되지 않는다.** 6대면 둘 다 1 ms 안팎이다. 계산 속도 주장의 근거는 2D 벤치마크이고, 3D는 "현실적 실행 가능성 + 흔들림이 적음"의 근거다. |

## 31.2 전체 그림

```
         ┌──────────────────────────── Gazebo Classic 11 ───────────────────────────┐
         │  창고 월드(선반 = 상자)   TurtleBot3 Burger × 6 (robot_1 … robot_6)          │
         │  장애물 상자(시나리오가 t초에 생성)                                          │
         └─────▲───────────────┬──────────────────────┬─────────────────────────────┘
       /robot_i/cmd_vel  /robot_i/odom          /robot_i/scan (LiDAR)
               │               │                      │
  ┌────────────┴───────────────▼──────┐   ┌───────────▼────────────┐
  │ cell_follower (로봇마다 1개)        │   │ obstacle_detector      │
  │  한 동작 = "다음 칸으로 돌고→직진"   │   │  보이는 물체 → 칸       │
  │  앞에 장애물 보이면 그 동작 보류      │   │  T_wait 동안 지켜봄     │
  └──────▲───────────────────┬────────┘   └───────────┬────────────┘
   이 동작 해도 됨  │           │ 동작 끝남 / 멈춤        │ /mapf/obstacle (확정)
         │                   ▼                        ▼
  ┌──────┴──────────────────────────────────────────────────────────────────┐
  │ mapf_executive (C++ 노드 1개)                                            │
  │   ├─ ADG 실행기: 약속을 확인하고 로봇마다 "다음 동작 해도 됨"을 내줌          │
  │   ├─ 재계획: 지금 모습 찍기 → 번호 다시 붙이기 → mapf_core replan()/full_replan() │
  │   └─ 기록: 사건·계산 시간·로봇 위치(10 Hz) → CSV, 재계획 입력 → JSON          │
  └──────────────────────────────────────────────────────────────────────────┘
                     ▲
           ┌─────────┴──────────┐
           │ scenario_runner     │  시나리오 JSON 읽기, 로봇 생성(로봇별 속도),
           │ (파이썬)            │  t초에 상자 생성, 끝나면 종료
           └─────────────────────┘
```

- **코어는 ROS를 모른다**(DESIGN.md §1). 코어와 ROS 사이에 **ROS를 모르는 C++ 라이브러리 `mapf_exec`**를 하나 둔다.
  여기에 칸↔미터 변환, **ADG 만들기·진행 상태**, **번호 다시 붙이기(31.6)**, **계획 검사**(시간표에 같은 칸·같은 번호, 맞바꾸기가 없나),
  **몸 검사**(실제 몸 모양끼리 겹치나, 몸이 가진 칸 밖으로 나갔나)를 넣고 **gtest로 시험**한다(Gazebo 없이).
- ROS 노드는 "토픽 받기 → `mapf_exec`/`mapf_core` 부르기 → 토픽 보내기"만 하는 얇은 껍데기다.
- 플래너와 ADG 실행기는 **한 노드**에 둔다. 나누면 "계획은 바뀌었는데 실행기는 옛 계획"인 순간이 생긴다.

## 31.3 격자 ↔ 실제 세계 — 칸 크기, 로봇 크기, 속도

TurtleBot3 Burger 제원(ROBOTIS 공개 값): 좌우 138 mm × 앞뒤 178 mm, 최고 0.22 m/s, 최고 회전 2.84 rad/s, LiDAR(LDS-01) 0.12~3.5 m, 5 Hz.

**몸 크기 — 무엇을 기준으로 삼나** (2026-11-26 확인, 초안의 "반지름 0.105 m"는 근거가 없어 고침)
- Gazebo 모델(`turtlebot3_gazebo/models/turtlebot3_burger/model.sdf`): 충돌 상자 0.14 × 0.14 m, 그 중심이 **회전 중심(바퀴 축)에서 0.032 m 뒤**.
  제자리에서 돌 때 쓸고 가는 원의 반지름 = 회전 중심에서 가장 먼 모서리까지 ≈ 0.124 m.
- Nav2 설정(`turtlebot3_navigation2/param/burger.yaml`)의 `robot_radius`는 0.1 m — 길 찾기용 근사라 검사 기준으로는 안 쓴다.
- **검사 기준 = 실제 제원 사각형** 앞뒤 0.178 × 좌우 0.138 m, 중심은 회전 중심에서 0.032 m 뒤(모델 값을 빌림. 실제 로봇은 8번에서 실측).
  회전 원 반지름 ≈ √((0.089 + 0.032)² + 0.069²) ≈ **0.14 m**. 시뮬레이션 모델보다 커서 더 보수적이다.

| 항목 | 추천 값 | 이유 |
|---|---|---|
| **칸 크기** | **0.5 m** (실험 바닥 크기를 알면 다시 확인) | 회전 원(0.14 m)이 칸 절반(0.25 m) 안에 들어가 **칸 안 여유 0.11 m**. 옆 칸 두 로봇 사이 최소 간격 0.22 m(0.5 − 2×0.14), 꽉 찬 선반 옆 칸에서 0.11 m |
| 칸 좌표 → 미터 | 칸 (x, y)의 중심 = (x × 0.5 + 0.25, y × 0.5 + 0.25) m | 월드 원점 = 격자 왼쪽 아래 모서리. y축 방향은 7-1에서 2D GUI 그림과 맞대 확인 |
| **로봇별 최고 선속도** | 시뮬레이션: 로봇마다 **0.12~0.22 m/s 중 하나**(시나리오 JSON에 적음) | 현장처럼 로봇마다 다르게. 실제 로봇은 각자 실제 값 |
| **로봇별 최고 각속도** | 0.8~1.5 rad/s 중 하나 | 위와 같음 |
| **작업 시간 흔들림** | 실제 작업 시간 = 계획 작업 시간 × (0.8~1.2 무작위) | 작업 시간은 "대략"만 안다는 현장 조건 |
| 동작 끝 판정 | 다음 칸 중심 3 cm 안 | 31.4의 "떠났다"도 이 판정으로 셈 |
| **기준 한 스텝 시간 `Δt_nom`** | 3.5초 (= 0.5 m ÷ 0.15 m/s + 회전 여유) | **작업 시간(초)을 스텝으로 바꿀 때만** 쓴다: 작업 스텝 = ⌈작업 초 ÷ `Δt_nom`⌉. 로봇 실행은 이 값에 묶이지 않는다 |
| `max_timestep` | 256 그대로 | 엔진 고정 설정(동점 규칙 larger-g 포함)은 2D와 같게 |

**알아 둘 한계 — 계획에는 "도는 시간"과 "로봇별 속도"가 없다.** 2D 계획에서는 직진·90° 꺾기·180° 뒤돌기가 모두 1스텝이고, 모든 로봇이 같은 빠르기다.
- **순서 안전에는 문제없다.** ADG가 시각이 아니라 순서를 지키게 하므로, 계획보다 늦거나 빨라도 같은 칸에 두 로봇이 들어가지 않는다.
  (몸이 실제로 안 겹치는지는 순서와 별개 — 31.4 "안전은 세 겹".)
- **효율에는 영향이 있다.** 계획상 짧은 길이 실제로는 회전이 많아 느릴 수 있다. 그래서 3D에서 **"계획 시간과 실제 시간이 얼마나 어긋나는지"를 측정**한다.
  많이 어긋나면 회전·로봇별 속도를 계획에 넣는 것을 검토한다. 이건 **저수준(A\* 상태에 방향 추가, 로봇별 동작 비용)과 고수준(한 동작이 여러 시각에 걸쳐
  칸을 차지하는 예약)을 둘 다 고치는 일**이라(연속 시간·운동학 MAPF, 예: CCBS), 이번 범위 밖이고 하더라도 스위치로 넣는다. 아니면 논문 한계로 적는다.

## 31.4 실행 방식 — ADG

### 왜 "각자 경로대로 가"면 안 되나

우리 코어는 **같은 칸·같은 시각**과 **맞바꾸기** 충돌만 막고, **바로 뒤따라 들어가기**는 허용한다. 계획은 시각 기준이다:

```
계획:   B가 t5에 칸 X를 떠나고, A가 t6에 X에 들어간다.
실제:   B가 회전 때문에(또는 느린 로봇이라서, 또는 작업이 3초 더 걸려서) 늦음
        → A는 계획 시각대로 X에 들어가다가 아직 X에 있는 B와 부딪힘
```

### ADG가 하는 일

계획에서 **시각은 버리고 순서만 약속으로 남긴다**:

> **약속**: "칸 X를 계획에서 먼저 쓰는 로봇이 X를 **떠난 뒤에야**, 다음 로봇이 X에 들어간다."

- 로봇마다 "동작 목록"을 만든다. 동작 = 한 칸 이동, 또는 목적지에서 작업. (계획의 "제자리 대기"는 동작이 아니다. 기다림은 약속이 만들어 준다.)
- 한 동작은 **자기 앞 동작이 끝나고 + 그 동작에 걸린 약속이 다 지켜졌을 때** 시작한다.
- 로봇은 동작마다 "끝났다"를 알린다(다음 칸 중심 도착, odom으로 자동 판단). **작업 할당이나 별도 통신은 필요 없다.**
- 결과: 로봇은 각자 속도로 연속 시간에 움직이고, **길이 겹치는 로봇끼리, 겹치는 칸에서만** 기다린다. 길이 안 겹치는 로봇은 서로 안 기다린다.

| | 동기식(초안에서 버린 안) | ADG |
|---|---|---|
| 누가 기다리나 | 매 스텝 모든 로봇 | 길이 겹치는 로봇끼리, 겹치는 칸에서만 |
| 로봇마다 다른 속도·회전·작업 시간 | 가장 느린 로봇에 다 맞춤 | 그대로 반영 |
| 시간 | 사실상 이산(2D와 같음) | 연속(실제 초로 잼) |

- ADG가 보장하는 것(Hönig 외 2019): 계획이 충돌 없으면 **실행에서도 한 칸을 두 로봇이 동시에 쓰지 않음**, **교착(서로 영원히 기다림) 없음**.
  속도가 얼마나 들쭉날쭉하든 성립한다. **이건 칸 단위의 보장이다.** 몸이 칸 밖으로 삐져나가는 것은 ADG가 모른다(바로 아래).
- 작업 시간도 자연스럽게 처리된다. 작업이 예상보다 길면 **그 칸을 다음에 쓸 로봇만** 더 기다린다.
- 안전 정지(마지막 방어선): cell_follower는 정면 ±30°, 0.25 m 안에 무언가 보이면 선다. ADG가 맞으면 발동할 일이 없으므로, **발동하면 기록하고 실패로 센다.**

### 안전은 세 겹 — ADG는 물리 충돌 검사기가 아니다 (2026-11-26)

사용자가 받아 온 의견: "회전 궤적·실제 몸 모양 때문에 겹치는 문제는 ADG만으로 해결 불가, 별도 충돌 검사 필요. ADG를 물리 충돌 검증기로 취급하지 말자."
→ **맞다.** ADG는 "어느 칸을 누가 먼저"만 알고 몸 모양은 모른다. 그래서 안전을 세 겹으로 나누고, 겹마다 무엇이 보장하고 어떻게 확인하는지 정한다.

| 겹 | 내용 | 무엇이 보장하나 | 어떻게 확인하나 |
|---|---|---|---|
| **(가) 계획 안전** | 시간표끼리 같은 칸·같은 번호가 없고 맞바꾸기도 없음, 장애물 칸을 안 밟음 | 코어 + 번호 다시 붙이기(31.6) | **재계획할 때마다 계획 검사**(`tools/independent_check.py`와 같은 규칙을 `mapf_exec`에 따로 구현). 통과 못 하면 실행하지 않고 실패로 셈 |
| **(나) 순서 안전** | 한 칸은 한 번에 한 로봇만 **가진다**. 이동 중인 로봇은 지금 칸과 다음 칸을 둘 다 가짐 | ADG | gtest + 변이 검사(약속 하나를 빼면 겹치는 장면이 생기는지) |
| **(다) 몸 안전** | 몸이 **자기가 가진 칸 밖으로 안 나감** | 칸 0.5 m + 돌고-가기(회전은 칸 중심에서만) + 추종 오차 < 0.11 m | **칸 이탈 검사**(기록에서) + 추종 오차 측정(7-2) |

**(나)와 (다)가 둘 다 맞으면 몸끼리 닿을 수 없다.** 가진 칸들은 서로 안 겹치고, 몸은 각자 가진 칸 안에만 있기 때문이다.

```
  ┌──────────── 칸 0.5 m ────────────┐
  │                                  │
  │        ╭──── 반지름 0.14 m ───╮   │   돌고-가기는 칸 중심에서만 돈다
  │        │      (회전 원)       │   │   → 회전 원이 칸 절반(0.25 m) 안에 들어감
  │        ╰──────────────────────╯   │   → 돌아도 자기 칸 밖으로 안 나감 (여유 0.11 m)
  │                                  │
  └──────────────────────────────────┘
  직진 중: 몸은 지금 칸 중심 → 다음 칸 중심 선 위로만 움직이므로 두 칸(둘 다 가진 칸) 안에 있다.
```

- **pure-pursuit를 안 쓰는 이유가 바로 (다)다.** 모서리를 둥글게 돌면 몸이 가지지 않은 대각선 칸을 스친다.
- **"떠났다" 판정은 "다음 칸 중심 3 cm 안"으로 둔다.** 그때 몸 전체가 이전 칸에서 빠져 있다. 나중에 효율 때문에 판정을 앞당기려면
  "몸 사각형 전체가 이전 칸을 벗어났나"로 정해야 한다(중심 거리로 대신하지 않는다).
- **확인은 결과로 따로 한다(검증과 보장을 섞지 않는다).** 위 세 겹이 맞게 설계됐더라도, 실행 기록에서 **실제 몸 사각형끼리 겹쳤는지**와
  **Gazebo 접촉**을 따로 센다(31.11). 충돌이 0이어도 칸 이탈이 있으면 "운이 좋았던 것"이므로 실패로 센다.
- 장애물 상자(0.4 m, 칸 경계에서 0.05 m 안쪽)·선반(칸을 꽉 채움)도 같은 방식으로 본다: 옆 칸 로봇과 최소 0.16 m / 0.11 m.
- 실제 로봇(8번)에서는 위치 추정 오차가 추종 오차에 더해진다. 여유 0.11 m를 넘으면 칸을 키운다(D1).

### 논문에 쓰는 법

"격자 계획은 Action Dependency Graph(Hönig 외 2019)로 실행하여 로봇마다 속도와 작업 시간이 달라도 계획의 칸 사용 순서를 지킨다."
→ **우리 기여가 아니라 검증된 표준 실행 방법을 썼다**고 밝힌다. 같은 계열: MAPF-POST(Hönig 외 2016, 시간 계획 그래프),
Switchable ADG(Berndt 외 2020~2023, Gazebo 검증), SMART 테스트베드(물리 시뮬레이터 + ADG 실행 서버). 31.14 참고.

## 31.5 장애물 — 언제, 어느 거리에서, 몇 초 기다렸다가 재계획하나

### 장애물 만들기

- 우리 범위는 "예기치 않은 장애물이 **나타나서 머문다**". 그래서 움직이는 사람(Gazebo actor)이 아니라 **0.4 m × 0.4 m × 0.4 m 상자**(떨어진 짐)를
  `/spawn_entity`로 한 칸 중심에 생성한다.
- 어느 칸: 2D 벤치마크와 같은 규칙 — **어떤 로봇의 앞으로 갈 길 위의 칸**(path 장면), 또는 작업 중 로봇이 길목에 선 장면(standing).
  단, **지금 로봇이 있거나 들어가는 중인 칸에는 만들지 않는다**(로봇 위에 상자가 생기는 장면은 없음).
- 언제: 시나리오 JSON에 "실제 시각 t초에 생성"으로 적는다.

### 발견 → 정지 → 지켜봄 → 확정 → 재계획

```
 t초        상자 생김
  │
  ▼  (어떤 로봇이 d_detect 안에 들어와야 보임)
 발견        로봇 R의 LiDAR가 지도에 없는 물체를 봄 → 칸 X로 바꿈
  │          (다른 로봇 자리의 점은 버림: 알려진 로봇 위치 ± 0.2 m)
  ▼
 정지        X가 R의 앞길이면, R은 X로 들어가는 동작을 시작하지 않고 지금 칸 중심에 선다
  │          (이미 그 동작 중이면 감속해 X 앞 d_stop에서 서고, 직전 칸으로 돌아간다)
  │          → R을 기다리는 약속이 걸린 로봇만 같이 늦어지고, 나머지는 계속 간다
  ▼
 지켜봄      T_wait초 동안 X에 계속 보이나 확인 (사람·지게차처럼 금방 비킬 수도 있으니까)
  │          ├─ T_wait 안에 사라짐 → 재계획 없이 R이 다시 출발 ("치워지는 장애물"은 범위 밖이라 실험 장면에는 넣지 않음)
  ▼          └─ 계속 있음 ↓
 확정        /mapf/obstacle 로 X를 알림 (모든 로봇이 공유하는 지도에 X를 막음)
  ▼
 재계획      31.6 — 지금 모습 찍기 → 번호 다시 붙이기 → replan() → 새 ADG → 다시 출발
```

| 파라미터 | 추천 기본값 | 실험에서 바꿀 값 | 뜻 |
|---|---|---|---|
| `d_detect` | 2.0 m (4칸) | 1.0 / 2.0 / 3.0 m | 이 거리 안의 물체만 장애물 후보로 봄. LDS-01 최대 3.5 m, 멀수록 점이 성겨 칸 판정이 흔들림 |
| `d_stop` | 0.30 m | 고정 | 동작 중에 발견했을 때 장애물 앞에서 서는 거리 |
| `T_wait` | 3초 | **0 / 3 / 10초** | 확정 전 지켜보는 시간. 길수록 잘못된 재계획은 줄지만 그동안 로봇이 서 있음 |
| 확정 조건 | `T_wait` 동안 LiDAR 스캔(5 Hz)의 90% 이상에서 보임 | 고정 | 한두 번 놓쳐도 확정되게 |

### 두 단계로 만든다

| | 7-4: 흉내 낸 발견 | 7-5: LiDAR로 발견 |
|---|---|---|
| 발견 방법 | Gazebo의 정답 위치로 "어떤 로봇과 상자 사이가 `d_detect` 이하이고 사이에 선반이 없으면 보였다"로 계산 | 로봇마다 LiDAR 점을 월드 좌표 → 칸으로 바꿔 판단 |

| 목적 | 흐름 전체를 센서 잡음 없이 먼저 맞춤 | 실제 로봇(8번)과 같은 흐름 |

## 31.6 재계획을 적용하는 방법 — "지금 모습 = 새 0번"

### 왜 필요한가

코어의 `replan(..., current_time = T)`은 **"모든 로봇이 각자 계획의 같은 번호 T에 있는 장면"**을 가정한다. 2D에서는 모두 같은 박자라 저절로 성립한다.
ADG에서는 로봇마다 계획을 진행한 정도가 다르다. 특히 **장애물을 본 로봇은 멈춰 있고 다른 로봇은 계속 간다.**

**예 1 — 옛 번호로는 맞출 수 없다** (A와 C는 서로 상관없음, 둘 다 1초에 한 칸)

```
         열:  1   2   3   4   5   6   7   8   9
  1행     A:  A → → → ■ → →                         A 계획: 1열 → 6열
  2행         (벽)
  3행     C:  C → → → → → → → →                     C 계획: 1열 → 9열
```

| 실제 시간 | A | C |
|---|---|---|
| 2초 | 3열(계획 2번째), ■를 보고 멈춤 | 3열(2번째) |
| 2~7초 | `T_wait` 5초 동안 기다림 | 계속 감 |
| **7초 (확정)** | **3열 = 계획 2번째** | **8열 = 계획 7번째** |

| 같은 번호 T를 고르면 | A는 계획상 | C는 계획상 | 가능? |
|---|---|---|---|
| T = 2 (A에 맞춤) | 3열 ✔ | 3열 ✘ (이미 8열, 뒤로 못 감) | ✘ |
| T = 8 (가장 앞선 로봇 + 1, **초안의 잘못된 안**) | 6열 ✘ (■를 지나야 함) | 9열 ✔ | ✘ |

→ 옛 번호는 버리고, **로봇이 지금 있는 칸에서 남은 길만 잘라 0번부터 다시 번호를 붙인다.**

```
              새 0번   새 1번   새 2번   새 3번
A 남은 길:     3열      4열■     5열      6열        → ■를 밟으므로 A만 영향받은 로봇
C 남은 길:     8열      9열                          → 그대로 유지, 멈추지 않음
```

**예 2 — 길이 겹치면 "그냥" 붙이면 부딪힌다** (교차로 X를 C가 먼저, D가 나중에 지나기로 계획됨)

```
           열:  1   2   3   4   5   6
  1행                       D
  2행           C → → → →  X  → →        C: 2행    왼쪽 → 오른쪽
  3행                       ↓             D: 4열 위 → 아래
  4행                       ↓
```

| 원래 계획 번호 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| C | 1열 | 2열 | 3열 | **X** | 5열 | 6열 | 6열 |
| D | 1행 | 1행 | 1행 | 1행 | 1행 | **X** | 3행 |

ADG 약속: "D는 C가 X를 떠난 뒤에 X에 들어간다." C가 느려서 6초에 아직 3열이고, D는 작업을 마치고 X 앞에서 약속대로 기다리는 중이다.
이때 다른 곳에서 장애물이 확정되어 재계획을 한다.

그냥 붙이면(남은 칸을 한 스텝에 한 칸씩):

| 새 번호 | 0 | 1 | 2 |
|---|---|---|---|
| C | 3열 | **X** | 5열 |
| D | 1행 | **X** | 3행 |

→ **새 1번에 둘 다 X = 충돌.** 남은 길을 칸 목록으로만 늘어놓아 "C가 먼저"라는 순서가 사라졌다. 이걸 `replan()`에 넣으면 C와 D(장애물과 상관없는 로봇)의
고정 경로가 장부에서 겹쳐 등록이 거절되고, 멀쩡한 상황에서 Tier를 넓히거나 안전망으로 빠지는 **틀린 결과**가 나온다.

**약속을 지키며 한 스텝씩 흉내 내서 붙이면:**

> 매 스텝, 각 로봇은 다음 동작을 하려고 한다. 그 동작에 걸린 약속(먼저 쓰기로 한 로봇이 그 칸을 떠났나)이 **이전 스텝까지** 지켜졌으면 한 칸 이동, 아니면 제자리 대기.

| 새 번호 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| C | 3열 | **X** | 5열 | 6열 | 6열 |
| D | 1행 | 1행 (대기) | 1행 (대기) | **X** | 3행 |

→ C가 X를 다 지난 뒤 D가 들어간다. 원래 계획과 순서가 같으니 충돌이 없다. 예 1(약속 없음)도 같은 규칙으로 처리된다(그냥 한 칸씩 가는 것과 같아짐).

### 전체 순서

```
① 확정 순간: 모든 로봇에게 "새 동작 시작 금지" (지금 하던 동작은 마저 끝냄)
② 지금 모습 찍기: 로봇마다 "지금 칸" = 서 있으면 그 칸, 이동 중이면 도착할 칸
                  작업 중이면 남은 작업 스텝 = ⌈남은 작업 초 ÷ Δt_nom⌉
③ 번호 다시 붙이기: 남은 ADG를 약속 지키며 한 스텝씩 흉내 → 새 0번부터의 경로 + 근무표
④ 재계획: replan(agents, 새 경로, 새 근무표, [장애물 칸], current_time = 0)
          (비교 실행이면 같은 입력으로 full_replan)
⑤ 새 계획으로 ADG를 새로 만들고 "시작 금지" 해제
```

- ①~⑤는 6대 규모에서 몇 ms라, 서 있지 않던 로봇은 사실상 멈추지 않는다(하던 동작을 끝내기 전에 새 계획이 나온다). 그래도 "시작 금지로 멈춘 시간"을 기록한다.
- 우리 방법이든 전체 재계획이든 **①~③은 똑같이** 하고 ④만 다르다 → 공정한 비교.
- **코어는 안 고친다.** ③은 `mapf_exec`가 하고, 위 예 1·예 2를 그대로 gtest로 만든다:
  "그냥 붙이면 충돌(그래서 이 기능이 필요함), 약속을 지키면 충돌 없음, 칸 사용 순서가 옛 계획과 같음,
  아무도 늦지 않았고 옛 계획에 '바로 뒤따라 들어가기'가 없으면 결과가 옛 계획의 남은 부분과 같음."
  (옛 계획에 바로 뒤따라 들어가기가 있으면, 이 규칙은 앞 로봇이 칸을 **다 떠난 다음 스텝**에 들어가게 하므로 그 자리에서 1스텝 늦어진다.
  더 안전한 쪽으로 늦어질 뿐 충돌은 안 생긴다. 실제 로봇도 ADG에서 똑같이 앞 로봇이 떠난 뒤에 들어간다.)
  테스트가 처음부터 통과하면 약속 확인을 일부러 빼서 테스트가 잡는지 확인한다(변이 검사).
- **번호 다시 붙이기는 재계획 알고리즘이 아니다.** 재계획 알고리즘(Tier 0~2, 안전망 ①②)은 "**누구를** 어떻게 다시 계획하나"를 정하고,
  번호 다시 붙이기는 그 전에 "실제 세계의 지금 모습을 **코어가 읽을 수 있는 시간표로 옮겨 적는**" 준비 단계다(영어로는 re-timing 정도).
  우리 방법과 전체 재계획이 똑같이 거치므로 **논문 기여로 세지 않고**, 3D 실험 방법 설명에 적는다.
- ②~④의 입력·출력을 **JSON으로 저장**한다 → 같은 입력을 2D 파이썬(`mapf_py`)으로 다시 돌려 **같은 재계획 결과가 나오는지** 확인할 수 있다(3D 연결이 맞는지 검사).

## 31.7 로봇 움직이기 — "돌고 → 직진 → 멈춤"

```
ADG가 "다음 동작 해도 됨" → 목표 = 다음 칸 중심
  ① 방향 오차 > 5° : 제자리 회전 (그 로봇의 최고 각속도 이하, 오차가 작아지면 줄임)
  ② 그다음         : 직진 (그 로봇의 최고 선속도 이하), 가면서 방향 오차에 비례해 살짝 보정(P 제어)
  ③ 중심 3 cm 안   : 정지 → "동작 끝" 보고
작업 동작: 목적지에 서서 (계획 작업 시간 × 흔들림)초 기다린 뒤 "동작 끝"
```

- DESIGN.md §5는 pure-pursuit로 시작한다고 적었지만, 격자 계획에는 돌고-가기가 더 맞다. pure-pursuit는 모서리를 둥글게 잘라 **계획에 없는 대각선 칸을 스친다.**
  돌고-가기는 항상 칸 중심선 위로만 다니고 칸 중심에서만 돈다 → 몸 안전 (다)(31.4).
- 직진 중 방향 보정은 중심선에서 벗어난 거리도 같이 줄인다(옆으로 밀리면 몸이 옆 칸으로 나가므로). 벗어난 거리는 10 Hz로 기록한다(추종 오차).
- 로봇마다 노드 1개(`cell_follower`, 네임스페이스 `/robot_i`), C++(rclcpp), 20 Hz.

## 31.9 월드와 로봇 대수

- **월드는 격자에서 자동 생성**: 파이썬 스크립트가 2D 지도를 읽어 막힌 칸마다 0.5 m 상자(선반)를 놓은 `.world`를 만든다 → 2D와 3D가 같은 지도.
- **기본 6대 = 실제 로봇 대수.** 지도 크기는 **실제 실험 바닥 크기가 정해지면 거기에 맞춘다**(예: 4 m × 4 m면 0.5 m 칸으로 8×8칸).
  그 전까지 시뮬레이션은 **10×10칸(5 m × 5 m), 선반 줄 2개**로 시작한다 — 6대가 서로 길이 겹칠 만큼 좁아야 재계획·ADG 대기가 실제로 생긴다.
- 여유되면 시뮬레이션만 8~12대(더 넓은 지도). Gazebo가 실시간보다 너무 느려지면(RTF < 0.3) 멈춘다.
  ADG는 순서만 지키므로 Gazebo가 느려져도 안전·순서 결과는 안 바뀐다. 다만 "실제 초" 지표는 시뮬레이터 시간으로 잰다.
- 이 노트북은 내장 GPU(AMD Lucienne)라 실험은 **화면 없이(gzserver만)**, 시연 영상만 화면을 켠다. 7-4(흉내 낸 발견)에서는 LiDAR를 꺼서 가볍게 할 수 있다.

## 31.11 무엇을 재나 — 지표와 실험 설계

**같은 시나리오 JSON을 `method: ours`와 `method: full`로 한 번씩.** (Park식·LNS2식은 3D에서 안 함.)

| 지표 | 뜻 |
|---|---|
| 성공 | 모든 로봇이 작업까지 끝냄 + **계획 검사 통과 + 몸 겹침 0 + 접촉 0 + 칸 이탈 0** + 비상 정지 0 |
| 계획 검사 (가) | 재계획마다 시간표 검사(같은 칸·같은 번호, 맞바꾸기, 장애물 칸, 이동 규칙) 통과 여부 |
| 몸 겹침 / 최소 간격 | 기록된 위치(10 Hz)마다 **실제 몸 사각형**(31.3)끼리, 몸–상자/선반이 겹치나 / 실행 중 몸 사이 가장 가까웠던 거리 |
| 접촉 | Gazebo 접촉(contact) 센서로 실제로 닿은 횟수. 몸 겹침 검사와 서로 맞는지도 본다 |
| **칸 이탈** (다) | 몸 사각형이 그 순간 ADG가 허락한 칸(지금 칸, 이동 중이면 다음 칸까지) 밖으로 나간 횟수와 최대 깊이(m) |
| 추종 오차 | 칸 중심선에서 벗어난 거리, 멈출 때 지나친 거리 — 최대값이 0.11 m 여유 안에 드나 |
| 재계획 계산 시간(ms) | `replan()`/`full_replan()` 한 번 (6대라 둘 다 작을 것) |
| **길이 바뀐 로봇 수** | 재계획 후 가는 칸 순서가 달라진 로봇 수 = 흔들림 |
| **재계획 때문에 멈춘 로봇 수·시간** | 장애물 앞에서 선 로봇 + 약속 때문에 같이 기다린 로봇, 각각 몇 초 |
| 장애물 처리 시간 | 등장 → 발견 → 확정 → 재계획 끝 → 다시 출발 (각 구간 초) |
| **다 끝난 시간(초)** / 합계 시간(초) | 마지막 로봇 작업 끝 / 로봇마다 작업 끝 시각의 합. **장애물 없는 같은 시나리오와의 차이 = 장애물 때문에 늘어난 시간** |
| 계획 vs 실제 | 계획 스텝 × `Δt_nom`과 실제 초의 차이 (31.3 한계를 수치로) |
| ADG 대기 | 약속 때문에 기다린 시간 합 |

- 실험 변수: 지도(넓은/좁은 통로), 장면(path/standing), `T_wait`(0/3/10초), `d_detect`(1/2/3 m). 로봇별 속도·작업 시간 흔들림은 시나리오마다 무작위(시드 고정).
- 시나리오 수: 조합마다 **20개 × 2방법**. 한 번에 약 3~5분(화면 없이) → 조합 하나에 2~3.5시간. 밤에 돌린다. 조합이 많으면 `T_wait`·`d_detect`는 기본 장면 하나에서만 바꾼다.

## 31.14 관련 연구 — 3D·실제 로봇에서 이산 계획을 어떻게 실행하나

| 연구 | 내용 | 우리와의 관계 |
|---|---|---|
| Hönig 외 2016, MAPF-POST (ICAPS) | 이산 계획 → 시간 계획 그래프, 최고 선속도·각속도를 넣어 실제 차동 구동 로봇에서 실행 | ADG의 전신 |
| **Hönig 외 2019, ADG (RA-L)** | 창고용. 기존 MAPF 플래너를 그대로 쓰고, 동역학을 모르거나 속도가 변하는 로봇에서도 견고하게 실행. 시뮬레이션 + 실제 로봇 | **우리가 쓰는 실행 방법** |
| Berndt 외 2020~2023, Switchable ADG | 실행 중 로봇 순서를 바꿔 지연을 줄임, Gazebo 검증 | 순서 바꾸기는 안 씀(우리는 재계획) |
| SMART 테스트베드 (arXiv 2509.10284) | 물리 시뮬레이터 + ADG 실행 서버 + 로봇별 제어기로 MAPF를 현실적으로 평가 | 31.2와 거의 같은 구조 |
| Analyzing Planner Design Trade-offs for MAPF under ADG-based Realistic Execution (arXiv 2512.09736) | 플래너들을 ADG 실행 위에서 비교 | **본문 읽기 필요** |
| Should I Replan? (arXiv 2604.25567) | ADG 실행 중 언제 다시 계획할지 | **본문 읽기 필요** — 31.6과 직접 겹침 |

- 확인한 범위: "실제 속도 차이를 다루는 MAPF 실행 연구의 표준 방법"이라는 데까지. "3D로 검증한 MAPF 논문 대부분이 ADG를 쓴다"고는 확인하지 않았다(경로점만 보내는 논문도 많음).
- 위 마지막 두 편은 27.4(3차 문헌)에 넣었다. **31.6(번호 다시 붙이기)이 이미 있는 방법인지**도 이 두 편에서 확인한다. 확인 전에는 새롭다고 주장하지 않는다.

## 31.15 바뀐 과정 (2026-11-25)

같은 날 초안 → 사용자 질문 3가지 → 이 판:

| 초안 | 사용자 지적 | 바꾼 것 |
|---|---|---|
| 동기식(모두 도착하면 다음 스텝)을 먼저, ADG는 나중 | "그러면 2D 이산 시뮬레이션과 뭐가 다른가. 현장 로봇은 속도·회전이 다 다르고 서로 기다리지 않는다" | **동기식을 버리고 처음부터 ADG**. 로봇별 속도·작업 시간 흔들림을 실험 조건에 넣음 |
| 장애물: 정답 알림 → LiDAR, 확정되면 바로 재계획 | "어느 시점·거리에서 보고, 몇 초 기다렸다 재계획하는지가 있어야 한다" | 발견 → 정지 → `T_wait` 지켜봄 → 확정 → 재계획, `d_detect`·`T_wait`를 실험 변수로 |
| (ADG는 실제 로봇용) | "작업 시간은 2D처럼 자리 차지 후 비키면 되니 ADG가 필요 없지 않나" | 작업 할당은 필요 없다는 데 동의. 다만 작업 시간이 "대략"이고 속도가 제각각이면 **누가 실제로 떠났는지 확인해야** 해서 ADG가 필요(31.4). ADG는 작업 할당 없이 계획에서 자동으로 나온다 |
| 재계획 시점 = "가장 앞선 로봇 스텝 + 1" | (설명을 준비하다 발견) | **틀렸음**: 장애물을 본 로봇은 멈춰 있어 옛 계획대로 따라올 수 없다(31.6 예 1). → "지금 모습 = 새 0번" + 약속을 지키는 번호 붙이기 |
| (2026-11-26) "ADG가 맞으면 실행도 충돌 없음", 충돌 기준 = 중심 거리 < 0.21 m(반지름 0.105) | 사용자가 받아 온 의견: "회전 궤적·몸 모양 겹침은 ADG만으로 해결 불가, 별도 충돌 검사 필요" | 맞음. ADG는 **칸 단위** 보장 → 안전을 세 겹(계획·순서·몸)으로 나눔(31.4). 몸 크기는 실제 제원 사각형 + 회전 중심 0.032 m 뒤로(회전 원 0.14 m, 칸 안 여유 0.11 m). 검사는 몸 사각형 겹침 + 접촉 + **칸 이탈** + 재계획마다 계획 검사. 0.105 m는 근거가 없어 버림 |

DESIGN.md에서 바꿀 것(이 문서를 구현에 들어갈 때 같이 고침):

| DESIGN.md | 이 설계 |
|---|---|
| 저수준 추종은 pure-pursuit로 시작 | 돌고-가기(31.7) |

## 31.17 번호 다시 붙이기 — 쉬운 자세한 설명

### 한 문장으로

> **로봇들이 가는 길(칸 순서)은 하나도 안 바꾸고, "지금"을 0번으로 해서 시간표만 새로 찍는 일.**
> 이때 "같은 칸을 먼저 쓰기로 한 로봇이 먼저"라는 순서만은 꼭 지킨다.

비유: **버스 노선은 그대로 두고, 시간표만 지금 시각 기준으로 다시 인쇄**하는 것이다. 버스가 늦기도 하고 빠르기도 해서 옛 시간표가 안 맞게 됐으니
지금 위치에서 다시 찍는다. 단 두 버스가 같은 정류장을 쓰면, 원래 먼저 서기로 한 버스가 먼저 서는 순서는 그대로 둔다.

### 왜 필요한가

- 코어(`replan()`)는 **"모든 로봇이 각자 시간표의 같은 번호 T에 있다"**는 말만 알아듣는다. 시공간 A\*와 예약 장부가 전부 "칸 + 번호"로 되어 있기 때문이다.
- 2D에서는 모두 같은 박자라 저절로 같은 번호에 있다 → 필요 없음.
- 3D(ADG)에서는 로봇마다 빠르기가 다르고, 장애물 앞에서 멈추고, 약속 때문에 기다린다 → **옛 번호로는 모두를 한 장면에 맞출 수 없다**(31.6 예 1).
- 그래서 재계획 직전에 실제 모습을 코어의 말(번호가 붙은 시간표)로 옮겨 적는다. **통역**에 해당한다.

### 무엇을 바꾸고 무엇을 안 바꾸나

| 바뀌는 것 | 안 바뀌는 것 |
|---|---|
| 번호(시간표), 그리고 그에 따른 "제자리 대기" 칸 | 로봇마다 앞으로 갈 **칸의 순서** |
| | 같은 칸을 쓰는 로봇들의 **먼저/나중 순서** |
| | 누가 장애물에 영향받는지 판단, 누구를 다시 계획할지 — 이건 다음 단계인 `replan()`의 일 |

옛 시간표의 "제자리 대기"는 일단 다 버린다. 기다림은 약속에서 다시 만들어진다(옛 대기는 옛 박자에 맞춘 것이라 지금은 의미가 없다).

### 순서 (다섯 단계)

```
① 시작 금지   장애물이 확정되면 모든 로봇에게 "새 동작 시작하지 마". 하던 동작은 마저 끝낸다.
② 지금 찍기   로봇마다 "지금 칸"을 정한다.
                - 서 있으면: 그 칸
                - 칸 사이를 가는 중이면: 도착할 칸 (①때문에 그 칸에서 멈추므로 이 기록이 계속 맞다)
                - 작업 중이면: 그 칸 + 남은 작업 스텝 = ⌈남은 작업 초 ÷ Δt_nom⌉
③ 번호 붙이기 새 0번 = 모두 지금 칸. 그다음 한 스텝씩 흉내:
                - 다음 동작이 "한 칸 이동"이면: 그 칸에 걸린 약속(그 칸을 먼저 쓰기로 한 로봇이 그 칸을 떠났나)을
                  **이전 스텝까지** 다 지켰으면 이동, 아니면 제자리 대기
                - 다음 동작이 "작업"이면: 제자리에서 남은 작업 스텝을 하나 줄임
                - 동작을 다 끝낸 로봇은 목적지에 그대로 있음
                모든 로봇이 동작을 다 끝내면 멈춤
④ 재계획      replan(로봇들, ③의 시간표, ③의 근무표, [장애물 칸], current_time = 0)
⑤ 다시 출발   새 계획으로 ADG를 새로 만들고 ①의 "시작 금지"를 푼다
```

### 예시 하나로 전부 보기

```
          열:  1   2   3   4   5   6   7
  1행          .   .   A   ■   .   .   .      A: 1행   을 오른쪽으로(목적지 7열). ■ 앞 3열에서 멈춰 있음
  2행          .   .   .   D   .   .   .      D: 4열을 아래로(목적지 4행   ). 교차로 X 앞에서 기다리는 중
  3행          .   C → ·   X   .   .   .      C: 3행   을 오른쪽으로(목적지 6열). 2열→3열로 가는 중
  4행          .   .   .   ·   .   .   E      E: 목적지(7열)에서 작업 중, 남은 7초
```

- 옛 계획의 약속: **X(3행 4열)는 C가 먼저, D가 나중.**
- ■ = 1행 4열에 확정된 장애물. `Δt_nom` = 3.5초.

**② 지금 찍기**

| 로봇 | 지금 상태 | 지금 칸 | 남은 동작 |
|---|---|---|---|
| A | ■ 앞에서 멈춤 | 1행 3열 | 4열 → 5열 → 6열 → 7열 |
| C | 2열 → 3열 이동 중 | **3행 3열**(도착할 칸) | X(4열) → 5열 → 6열 |
| D | X 앞에서 약속 때문에 대기 | 2행 4열 | X → 4행 4열 |
| E | 작업 중, 남은 7초 | 4행 7열 | 작업 ⌈7 ÷ 3.5⌉ = **2스텝** |

**③ 번호 붙이기 (한 스텝씩 흉내)**

| 새 번호 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| A | 3열 | 4열 ■ | 5열 | 6열 | 7열 (끝) |
| C | 3열 | **X** | 5열 | 6열 (끝) | 6열 |
| D | 2행 | 2행 (대기: C가 아직 X를 안 떠남) | 2행 (대기: C가 이번 스텝에 막 떠남) | **X** | 4행 (끝) |
| E | 작업 (2 남음) | 작업 (1 남음) | 작업 끝 | 7열 | 7열 |

한 칸씩 확인:
- **A**: 아무 약속이 없어서 한 칸씩 간다. 1번에 ■ 칸에 들어가는 것으로 적히는데, **일부러 그대로 둔다.** 번호 붙이기는 통역만 하고,
  "■를 밟으니 다시 계획해야 한다"는 판단은 ④ `replan()`의 일이다.
- **C**: 약속을 기다릴 일이 없어서 한 칸씩 간다.
- **D**: X에 들어가려면 "C가 X를 떠났다"가 **이전 스텝까지** 일어나야 한다. C는 2번에 X를 떠난다 → D는 3번에 X에 들어간다.
  만약 약속을 무시하고 그냥 한 칸씩 붙였으면 1번에 C와 D가 둘 다 X에 있다 = 충돌(31.6 예 2).
- **E**: 남은 작업 2스텝 동안 제자리, 그 뒤로도 목적지에 그대로.

**④ 재계획**: 이 표를 `replan(..., current_time = 0)`에 넣는다.
- 시간표가 ■를 밟는 로봇은 **A뿐** → A만 영향받은 로봇. A는 ■와, C·D·E의 시간표를 피해 새 길을 받는다(예: 2행로 내려가 D가 4열을 비운 뒤 지나감).
- C·D·E는 시간표 그대로 = **길이 안 바뀐다.** 이게 우리 선택적 재계획의 효과다. 전체 재계획이었다면 같은 표를 받아 4대를 모두 다시 계획한다.

**⑤ 다시 출발**: 새 계획으로 ADG를 다시 만든다.
- **번호는 실제 시각이 아니다.** "새 1번"의 A와 "새 1번"의 C가 실제로 같은 순간에 움직인다는 뜻이 아니다. 실제 로봇은 ADG로 **순서만** 지키며 각자 속도로 간다.
- E의 실제 작업이 7초가 아니라 9초 걸려도 괜찮다. E의 칸을 다음에 쓸 로봇이 있으면 그 로봇만 E가 떠날 때까지 기다린다.

### 왜 이렇게 만든 시간표는 안전한가

1. **충돌이 없다**: 같은 칸을 쓰는 두 로봇은 "앞 로봇이 다 떠난 다음 스텝에 뒤 로봇이 들어간다". 그래서 같은 번호에 같은 칸이 없고,
   맞바꾸기(서로 칸을 바꿔 지나가기)도 순서가 정해져 있어 생기지 않는다.
2. **순서가 옛 계획과 같다**: 약속을 그대로 따랐으므로, 실제 로봇이 ADG로 움직이는 순서와도 같다.
3. **반드시 끝난다**: ADG에는 "서로가 서로를 기다리는" 고리가 없다(Hönig 외 2019). 그래서 흉내가 무한히 돌지 않는다.
4. **늦은 로봇이 없으면 옛 시간표와 거의 같다**: 다른 점은 옛 계획에 "바로 뒤따라 들어가기"가 있던 자리에서 1스텝 늦어지는 것뿐이다(더 안전한 쪽).

### 이것은 우리 재계획 알고리즘인가?

**아니다.** 재계획 알고리즘(Tier 0~2, 안전망 ①②)은 "**누구를** 어떻게 다시 계획하나"이고, 번호 다시 붙이기는 그 앞에서 하는 **통역**이다.
2D에서는 필요 없고, 우리 방법과 전체 재계획이 똑같이 거친다. 그래서 논문 기여로 세지 않고 3D 실험 방법에 한 문단으로 적는다.
(이미 있는 방법인지는 27.4에 넣은 두 논문에서 확인한다.)

### 테스트로 확인할 것 (7-4)

- 위 예시를 그대로 gtest로 만든다: D가 3번에 X에 들어가는가, E가 2스텝 작업하는가, A·C의 칸 순서가 그대로인가.
- 약속 확인을 일부러 빼면 "1번에 C와 D가 X에서 충돌"을 테스트가 잡는가(변이 검사).
- 무작위 시나리오 여러 개: 결과 시간표에 충돌이 없고, 칸 사용 순서가 옛 계획과 같은가.

## 31.19 시나리오 JSON 형식 (`mapf_scenario_v1`, 7-1에서 정함)

3D 실험 한 판의 모든 입력을 담는 파일이다. 같은 파일로 `ours`와 `full`을 돌리고, 같은 파일을 2D 코어(`mapf_py`)로도 돌릴 수 있다.
만드는 명령: `ros2 run mapf_gazebo make_scenario --map corridor --size 10 --robots 6 --seed 1 --out 파일.json`.
저장소에 있는 것: `ros2/mapf_gazebo/scenarios/corridor10_r6_s1.json`, `open10_r6_s1.json`.

| 칸 | 뜻 |
|---|---|
| `format` | `"mapf_scenario_v1"` (읽을 때 확인) |
| `name`, `map_kind`, `seed` | 이름(`corridor10_r6_s1` = 좁은 통로 10×10, 6대, 시드 1), 지도 종류, 시드 |
| `cell_size`, `dt_nom_s` | 칸 크기 0.5 m, 기준 한 스텝 시간 3.5초(작업 초 ↔ 스텝 변환에만, 31.3) |
| `map` | 글자 줄 목록, `rows[y][x]`, (0,0) = **왼쪽 위**, `#` = 선반. 2D 코어와 똑같은 형식. 벤치마크와 같은 규칙(`grid.make_map_rows`)을 작은 크기에 적용 |

### 31.20 보충 — 화면 방향과 월드 파일 (2026-11-26, 사용자 질문)

**화면이 90° 돌아가 보였던 이유.** 사용자가 `gui:=true`로 띄워 위에서 본 화면이 2D 그림과 90° 달랐다. 스크린샷의 로봇 6대 위치를 재 보니

**월드 파일은 띄울 때마다 새로 만든다.** `scenario.launch.py`가 시나리오 JSON의 `map`에서 `.world`를 임시 폴더에 만들어 바로 띄운다(수 KB, 1초도 안 걸림).
- 이유: **시나리오 JSON 하나만 원본**으로 두기 위해서다. `.world`를 따로 저장해 두면 지도를 바꿨을 때 옛 `.world`가 남아 2D와 3D 지도가 어긋날 수 있다.
  격자에서 매번 만들면 "2D 지도 = 3D 월드"가 코드로 보장된다(31.9).
- 같은 지도의 시나리오(시드만 다른 것)는 같은 `.world` 내용이 나온다(월드는 `map`에만 달렸고, 로봇은 따로 생성).
- 시나리오를 만드는 명령(`make_scenario`)은 JSON만 만든다. `.world`가 파일로 필요하면(예: Gazebo로 바로 열기, 실제 로봇용 지도 그림)
  `ros2 run mapf_gazebo grid_to_world 시나리오.json --out 파일.world`로 저장할 수 있다.

**사고 기록.** 같은 날 AI가 점검하려고 Gazebo를 띄웠을 때 사용자가 띄워 둔 Gazebo가 이미 있었다. 새 gzserver는 바로 죽었고, 점검은 사용자의 Gazebo를 대상으로
돌았으며, AI의 종료 명령(`pkill -f "ros2 launch mapf_gazebo"`)이 사용자의 Gazebo까지 껐다. → CLAUDE.md에 "먼저 확인, 자기 PID로만 끄기" 규칙을 넣음.

### ADG를 만드는 법 (사용자와 확인한 설계)

1. **계획 → 동작 목록**: 로봇마다 시간표에서 칸이 바뀌는 순간만 이동 동작으로 만든다. 중간의 제자리 대기는 버린다(기다림은 약속이 만든다).
   경로 끝 목적지의 작업 스텝은 작업 동작 하나(실제 시간 = 작업 스텝 × `Δt_nom` × `service_factor`).
2. **약속(화살표)**: 같은 로봇은 순서대로. 로봇 사이는 "동작 a가 칸 c를 떠나고, 다른 로봇의 동작 b가 **같거나 늦은 계획 시각에** c로 들어가면 a → b".
   b는 a가 끝난 뒤, 즉 앞 로봇이 다음 칸 중심에 도착한 뒤에야 출발한다(31.4 "떠났다" 판정).
3. **실행**: 같은 로봇의 앞 동작이 끝났고 들어오는 약속이 모두 끝난 동작만 내준다. 그 외에는 로봇마다 자기 속도로 간다.
4. 화살표는 늘 계획상 먼저 → 나중이라 고리가 없다 → 교착 없음. 계획이 맞다는 전제가 필요해서 실행 전에 계획 검사 (가)를 돌린다.

### 처음 계획은 실행 중에 만들지 않는다 (사용자 지적, 2026-11-27)

PP + 시공간 A\*는 처음 계획부터 실패할 수 있다(26.6: 좁은 통로 200대에서 76.5%). 그래서 실행기는 `plan()`을 부르지 않는다.
`make_scenario`가 **`plan()`이 성공하는 배치가 나올 때까지 다시 뽑아** 성공한 계획을 `initial_plan`에 저장하고(`placement_attempts`에 몇 번째인지),
실행기는 그 저장된 경로를 읽는다. 없으면 시작하지 않는다. 우리 연구의 설정("처음 계획은 무엇으로 만들었든 로봇별 경로만 받는다", 26.7)과도 같다.

2. **계산 시간은 3D 규모(6대)에서 차이가 없다**(둘 다 1 ms 미만) — 31.1에서 예상한 대로. 속도 주장의 근거는 2D.
3. **좁은 통로에서 우리 방법이 다 끝난 시간이 더 길다(137 vs 88초).** 우리 방법은 robot_3 한 대만 다시 계획하고 나머지 5대의 길·시간표를
   그대로 고정하므로 robot_3이 그 사이를 피해 크게 돌아간다(새 계획 20 vs 15스텝). robot_3의 우회 길이 robot_4와 얽혀 robot_4도 늦어졌다(71.9 vs 48.0초).
   전체 재계획은 이미 도착해 있던 robot_5까지 잠깐 비켜 세워(길이 바뀐 로봇 3대) robot_3에게 짧은 길을 줬다.
   → **"덜 흔들림(바뀐 로봇 1대 vs 3대)"과 "끝나는 시간"이 맞바뀐다.** Tier 0에서 A\*가 길을 찾으면 넓히지 않으므로(우리 설계),
   "길은 있지만 매우 긴" 경우가 그대로 나온다. 2D에서도 SOC를 비교한 열이 있으니(`selective_replan_soc` vs `full_replan_soc`) 9번 전에 함께 볼 것.
4. 넓은 맵에서는 두 방법이 같다(우회가 짧음).
5. 이 결과는 시나리오 3개 × 1번이고, 장애물 칸을 지나는 로봇이 각 1대뿐이다(6대 × 10×10에서 "번호 3 이후" 조건 때문). 일반화하면 안 된다.

### 31.23 보충 — 다시 보기에서 로봇이 번쩍임, 확대가 안 됨 (2026-11-27 사용자 확인)

- **번쩍임**: 처음에 `ros2 bag play … --clock`으로 안내했는데, 녹화 안에 이미 Gazebo 시뮬레이터 시계(`/clock`)가 있어서 재생기가 녹화 때 컴퓨터 시각으로
  두 번째 `/clock`을 또 냈다 → 시계가 0초대와 17억 초대를 오감(화면 없이 같은 조건으로 재 보니 8초에 284번 거꾸로 감) → RViz가 TF를 계속 지워 로봇이 사라졌다 나타남.
  **`--clock` 없이 재생하면 0번**. 안내와 `replay.launch.py play:=`를 고침.
- **확대·축소가 안 됨**: 만든 RViz 설정에 마우스 조작 도구(Interact, Move Camera)가 없었다 → 넣음. 휠 = 확대·축소, 가운데 버튼 끌기(또는 Shift + 왼쪽 끌기) = 옮기기,
  왼쪽 끌기 = 돌리기. Views 패널(배율·중심을 숫자로, Zero = 처음 시점), Time 패널(지금 시각 — 이상한 장면의 시각을 알려 줄 때)도 넣음.
- **TF 연결 자체는 맞았다**: 녹화 재생 중 `world → robot_1/base_footprint` = (3.75, 0.25) m = 9행 7열 중심.
- 다시 보기에서 Gazebo 화면(`gui`)은 볼 수 없다 — Gazebo는 녹화를 재생하지 않는다. 실행할 때 `scenario.launch.py gui:=true`로 본다.

### 31.23 보충 2 — "모두 한 스텝씩 맞춰 움직이는 것 같다" (2026-11-27 사용자 질문)

다시 보기를 본 사용자가 "마지막 로봇의 한 스텝이 끝날 때까지 모두 기다리는 느낌, 그러면 ADG가 왜 필요하냐"고 물음. 7-3 좁은 통로 기록으로 확인:
- **동기식이 아니다**: 3번째 칸을 끝낸 시각이 robot_2 12.0초, robot_1 14.5초(회전) — robot_2는 기다리지 않고 다음 칸으로 감.
  약속 때문에 기다린 시간은 대부분 0~0.3초, robot_4만 10.2초(5행 5열 교차로에서 다른 로봇이 먼저 지나가길 기다림 = ADG가 하는 일).
- **그런데 거의 칸마다 선다**: 이동 33번 중 25번 속도가 2 cm/s 아래로. 동작 하나 = 한 칸이고, follower가 칸 중심에서 감속해 완전히 선 뒤 DONE을 보고하기 때문.
  6대가 0초에 같이 출발, 속도 0.17~0.22 m/s로 비슷 → 모두 약 4초마다 "서고 → 출발" → 동작 33개 중 18개가 다른 로봇과 0.2초 안에 같이 끝남 → 같은 박자처럼 보임.
- **고칠 것(다음 세션 첫 작업)**: 곧게 가는 길은 멈추지 않기 — 칸 중심에 닿기 전에, 같은 로봇의 다음 동작이 이미 내줄 수 있고(약속이 다 지켜짐) 같은 방향이면 미리 내줌,
  follower는 감속하지 않고 중심을 지나며 DONE. 꺾을 때(제자리 회전)·약속 때문에 기다릴 때만 선다. 다른 로봇에게 "떠났다"는 그대로 "다음 칸 중심을 지남"이라 안전은 같다
  (곧게 가는 몸은 지금 칸과 다음 칸 안). 바꾼 뒤 7-3·7-4를 다시 돌려 안전 0과 다 끝난 시간 변화를 볼 것. 스위치(기본 켬/끔은 그때 정함)로.
