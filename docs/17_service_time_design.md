# 17. 작업 시간(Service Time) 설계 — 도착한 로봇은 작업 중인가, 대기 중인가

> 작성: 2026-09-15. 15장 15.10의 **문제 4**를 해결하기 위한 설계 문서다. 코드를 쓰기 **전에** 무엇을,
> 왜, 어떻게 바꾸는지 전부 정리한다. 이 문서를 이해한 뒤에 코드로 넘어간다.
>
> 먼저 16장(코드 실행 순서 따라가기)을 읽었다고 가정한다. 예시도 16장의 K·W·Z를 그대로 쓴다.

## 17.0 한 장 요약

| 질문 | 답 |
|---|---|
| 무엇이 문제인가? | 지금은 도착한 로봇이 "작업 중"인지 "대기 중"인지 구분하지 않는다. 그래서 **작업 중인 로봇도 구조 로봇으로 불려 끌려 나갈 수 있다.** |
| 무엇을 넣나? | 로봇마다 **작업 시간**(도착해서 몇 스텝 동안 일하는지). |
| 작업 중에는? | **절대 안 움직인다.** 불려도 **작업이 끝난 뒤에** 비켜 준다. |
| 작업이 끝나면? | 지금과 같다. 목적지에 머물지만(Tail) 불리면 비켜 줄 수 있다. |
| 작업 시간 = 0이면? | **지금 코드와 완전히 같게** 동작한다. 기존 테스트 52개가 그대로 통과해야 한다. |
| 바뀌는 곳 | A\* 도착 판정 1곳, 재계획의 "출발 시각" 계산, 작업 중 로봇 먼저 예약, 작업 일정 기록 |

## 17.1 왜 필요한가 — 16장 예시로 다시 보기

16장에서 K는 (4,1)에 도착해 있었고, W의 길을 막아 구조 로봇으로 불렸다. 그리고 t5에 (4,0)으로
비켰다가 t6에 돌아왔다.

- K가 **작업을 끝내고 쉬는 중**이었다면 → 비켜 줘도 된다. 문제없다.
- K가 **짐을 내리는 중**(예: t0~t8 작업)이었다면 → t5에 비키는 건 **현실에서 불가능**하다.

지금 코드는 이 둘을 구분할 방법이 없다. 도착한 로봇은 모두 "주차 중"이라고 가정한다.

## 17.2 관련 연구에서 무엇을 가져오나

| 연구 | 그 연구가 하는 것 | 우리가 가져오는 것 | 우리와 다른 점 |
|---|---|---|---|
| **MCPF with Heterogeneous Task Duration** (Zhang 외, 2023) | 로봇이 목표 칸에서 **작업 시간 동안 머문다.** 작업 시간은 로봇·목표마다 다를 수 있다. 계획이 끝난 뒤 덧붙이는 방법(최적 보장 없음)과 **계획할 때부터 고려하는 방법**(최적 보장)을 비교한다 | "작업 = 목표 칸에 머무는 시간"이라는 정의. **계획할 때부터 고려**(A\*가 작업 구간까지 비어 있는지 확인) | 오프라인 계획만. 실행 중 장애물 재계획은 없다 |
| **MAPF for Schedule Constrained Automation** (SoCS) | 목적지 도착 후 **처리 시간**을 시간 축 위의 사각형(구간)으로 표현 | 작업을 **시간 축 위의 구간 [시작, 끝]**으로 기록하는 방식(→ `TaskWindow`) | 장애물 재계획이 아니라 스케줄 제약이 주제 |
| **MAPD** (Ma 외, 2017) | 창고에서 로봇이 계속 작업을 받는다. 배달 칸에 **도착하면 작업 완료**(작업 시간 0) | 작업 시간 0 = 지금 코드. 우리 설계는 이것의 일반화 | lifelong(계속 새 작업). 우리는 로봇당 작업 하나 |
| **Park 외 2026** (*Sensors*) | 공장에서 장애물의 영향을 받는 로봇만 다시 계획. 작업을 마치면 바로 새 작업 | "영향받은 로봇만 재계획"(우리와 같다) | **작업 시간이 없고**, 재계획이 **실패했을 때 처리가 없다**. 우리 차별점이 여기서 나온다 |
| **FlexSIPP** (Hanou 외, SoCS 2026) | 로봇이 **늦어졌을 때** 그 로봇 하나만 다시 계획하고, 다른 로봇의 여유 시간을 활용 | 이번에는 가져오지 않는다 | 원인이 장애물이 아니라 지연. 나중에 "작업 시간이 예상보다 길어지는 경우"를 다룰 때 참고할 수 있다 |

**한 줄 정리**: 작업 시간이라는 **개념**은 기존 연구에서 가져온다. 우리가 새로 하는 것은
**"실행 중 장애물 → 선택적 재계획 → 실패하면 원인 로봇을 불러 비키게 함"에서, 작업 중인 로봇은 작업이
끝날 때까지 안 움직이게 하는 것**이다.

## 17.3 모델 — 쉬운 말로

### 가정 (이번 설계의 범위)

1. 로봇마다 **작업이 하나**다. 목적지에 도착하면 작업하고, 끝나면 그 자리에 **주차**한다(지금처럼 one-shot).
2. 작업 시간은 로봇마다 **미리 알려진 고정값**이다(스텝 단위). 예상보다 길어지는 경우는 다루지 않는다.
3. **작업 중**에는 절대 안 움직인다.
4. **주차 중**에는 목적지를 차지하고 있지만(Tail), 불리면 비켜 줄 수 있다(지금과 같다).
5. 장애물은 지금처럼 **예기치 않은 장애물**(나타나서 그 자리에 머묾)이다.

### 로봇 한 대의 시간 축

```
 이동 중                 작업 중 (못 비킴)          주차 중 (비켜 줄 수 있음)
 ─────────────────▶ ■■■■■■■■■■■■■■■■■■■ ░░░░░░░░░░░░░░░░░░░░░ ▶ max_timestep
                   ↑                     ↑
                작업 시작 = 도착         작업 끝 = 도착 + 작업 시간
                (start)                 (end, 이 시각부터 움직일 수 있음)
```

어떤 시각 T에 로봇은 셋 중 하나다.

| 상태 | 조건 | 재계획할 때 |
|---|---|---|
| **이동 중** | T < start | 지금 위치에서 다시 계획. 도착하면 **작업 시간만큼** 머물러야 한다 |
| **작업 중** | start ≤ T < end | **end까지는 제자리 고정.** end부터만 다시 계획할 수 있다. 작업은 이미 하고 있으니 다시 하지 않는다 |
| **주차 중** | end ≤ T | 지금 위치에서 다시 계획(지금과 같다). 작업은 끝났으니 다시 하지 않는다 |

**작업 시간 = 0이면** start = end라서 "작업 중"인 순간이 없다. 그래서 지금 코드와 똑같다.

### 시간 계산 약속

- 로봇이 t_a에 도착하고 작업 시간이 S면, 경로에는 **(목적지, t_a), (목적지, t_a+1), …, (목적지, t_a+S)**가 들어간다.
- 작업 구간은 **[t_a, t_a+S)** = S스텝이다. **t_a+S부터** 움직일 수 있다(그 스텝에 다음 칸으로 이동하면 t_a+S+1에 도착).
- 예: t_a=0, S=8 → 경로에 (4,1)t0 … (4,1)t8, 작업은 t0~t7, **t8부터 움직일 수 있음**, 가장 빨리 떠나면 t9에 옆 칸.

## 17.4 설계 결정 — 하나씩, 이유와 함께

### 결정 1. 로봇마다 작업 시간을 받는다

```cpp
struct Agent {
    int id{0};
    Cell start{};
    Cell goal{};
    int service_time{0};   // 새로 추가: 도착 후 작업하는 스텝 수. 기본 0 = 지금과 같음
};
```

**왜 기본값 0?** 기존 코드(벤치마크, GUI, 테스트)를 하나도 안 고쳐도 지금처럼 동작한다.

### 결정 2. 경로에 작업 구간을 포함한다

A\*가 돌려주는 경로 끝에 **작업 시간만큼 목적지에 머무는 칸**을 붙인다.

```
작업 시간 0:  … (5,2)t7 (6,2)t8
작업 시간 3:  … (5,2)t7 (6,2)t8 (6,2)t9 (6,2)t10 (6,2)t11
                              └──── 작업 (t8~t10) ────┘  t11부터 움직일 수 있음
```

**왜?** 경로만 봐도 "이 로봇이 언제 어디 있는지"가 정확하다. `register_path`, `position_at`, GUI,
충돌 검사 코드를 **바꿀 필요가 없다.** 작업 구간도 그냥 "목적지에 머무는 칸"이기 때문이다.

**대가**: 경로 비용 합(도착 시각의 합)에 작업 시간이 더해진다. 로봇마다 작업 시간은 고정이라, 모든
방법에 **같은 양**이 더해진다. 방법끼리 비교하는 데는 영향이 없다.

### 결정 3. 작업 일정을 경로와 **따로** 기록한다

```cpp
struct TaskWindow {
    int start{0};   // 작업 시작 = 도착 시각
    int end{0};     // 작업 끝 = 이 시각부터 움직일 수 있음 (start + 작업 시간)
};
using TaskSchedule = std::unordered_map<int, TaskWindow>;   // 로봇 id → 작업 구간
```

**왜 경로만으로는 안 되나?** 경로에는 "목적지에 머물러 있다"만 보이고, 그게 **작업인지 주차인지는
안 보인다.** 16장의 K를 보자(작업 시간 5라고 하자).

```
처음 경로:        (4,1)t0 (4,1)t1 … (4,1)t5                    ← t0~t4 작업, t5부터 주차
구조된 뒤 경로:    (4,1)t0 … (4,1)t6 (4,0)t7 (4,1)t8           ← 비켰다가 t8에 돌아옴
```

"경로 끝에서 작업 시간만큼 앞이 작업 시작"이라고 계산하면, 구조된 뒤 경로에서는 작업 시작이
8 − 5 = **t3**으로 나온다. 실제로는 t0에 시작해 t5에 끝났는데 말이다. 다음 장애물 때 K를 **"작업
중"으로 잘못 판단**하게 된다. GUI는 재계획을 여러 번 이어서 하므로, 이 실수가 실제로 생긴다.

그래서 작업 구간은 **한 번 정해지면(도착하면) 따로 기억**해야 한다.

### 결정 4. 작업 중인 로봇은 "작업이 끝나면 비켜 줘"가 된다

작업 중인 로봇이 길을 막고 있을 때 두 가지 선택이 있다.

| 선택 | 뜻 | 장점 | 단점 |
|---|---|---|---|
| (가) 아예 안 부른다 | 작업 중인 로봇은 구조 후보에서 뺀다 | 단순하다 | 작업이 곧 끝나도 기다리는 선택을 못 한다. 무조건 돌아가야 한다 |
| **(나) 불러도 되지만 작업 끝난 뒤에만 움직인다** | 남은 작업 구간은 고정, 그 뒤부터만 다시 계획 | "조금 기다렸다 지나가기"가 가능. (가)가 할 수 있는 건 다 할 수 있다 | 아래 결정 5가 필요하다 |

**(나)를 고른다.** 17.5의 경우 2(K가 t8까지 작업 중, W의 우회로는 K 자리뿐)로 비교하면 차이가 분명하다.

| | 일어나는 일 | 결과 |
|---|---|---|
| (가) | W 막힘 → K는 작업 중이라 후보에서 빠짐 → 부를 로봇 없음 → 안전망 → 안전망에서는 K가 W보다 먼저 계획돼 제자리에 머묾 → W 또 막힘 | **실패** |
| (나) | K를 부름 → K는 t8까지 제자리, 그 뒤 비킴 → W는 기다렸다 t9에 통과 | **성공** (W t12 도착) |

(가)에는 "기다렸다 지나가기"라는 선택지 자체가 없어서, 풀 수 있는 문제를 못 푼다.

이유가 하나 더 있다. **전체 재계획**(비교 기준, 안전망)은 모든 로봇을 다시 계획한다.
여기서도 작업 중인 로봇을 움직이면 안 되므로, 어차피 "남은 작업은 고정" 규칙이 **반드시** 필요하다.
그 규칙이 있으면 (나)는 거의 공짜로 된다.

이것은 문제 3(양보)과도 이어진다. 그림 9에서 114가 작업 중이라면, 67은 "114의 작업이 끝날 때까지
기다렸다 지나가기"와 "크게 돌아가기" 중 **더 빠른 쪽**을 A\*가 알아서 고른다.

### 결정 5. 재계획을 시작할 때 **작업 중인 로봇의 남은 작업**을 장부에 먼저 적는다

```
try_replan_set / full_replan 시작:
  1. 장부 비우기
  2. 새 장애물 적기
  3. [새로 추가] 지금 작업 중인 로봇마다: 목적지를 T부터 end까지 예약 (주인 = 그 로봇)
  4. (지금처럼) 순서대로 등록 / A*
```

**왜 먼저?** 10장에서 본 "순서 문제"와 똑같은 원리다. 16장 Tier 1의 순서는 Z → W → K였다. K가 작업
중이라 해도 K는 **W 다음에** 계획된다. 먼저 적지 않으면:

```
W의 A*:   장부에 K가 없다 → t5에 (4,1)을 지나가는 길을 고른다 (K는 작업 중인데!)
K 등록:   K의 남은 작업 (4,1)t3~t8이 W의 (4,1)t5와 겹친다 → 거절 → 실패
```

먼저 적어 두면 W의 A\*가 **처음부터** K의 작업을 본다. 그래서 기다리거나 돌아가는 길을 찾는다.

**고정 로봇은?** 고정 로봇은 옛 경로 전체를 등록하니, 그 안에 작업 구간이 이미 들어 있다. 3번에서 한
번 더 적어도 **자기 칸이라** 문제없다(`reserve_if_unowned`는 자기 것이면 통과).

**구현하며 추가한 것 (2026-11-17)**: 작업 중인 로봇이 구조 로봇이 되어 **자기 차례에 A\*를 돌릴 때는, 자기가
먼저 적어 둔 남은 작업 칸을 잠깐 지운다**(`release_ongoing_task`). 안 지우면 A\*가 "목적지가 작업 끝 시각까지
예약돼 있다"고 보고(자기 예약인데도) 도착을 한 스텝 늦게 인정해서 경로가 쓸데없이 한 칸 길어진다. 지운 칸은
바로 뒤 `register_path`가 새 경로(남은 작업 칸 포함)로 다시 적는다. 테스트
`WorkingAgentDoesNotWaitAnExtraStepForItsOwnReservation`이 이것을 확인한다(지우기를 끄면 경로가 t8이 아니라 t9에서 끝남).

**원래 방식(`kPriority`)에도 도움이 된다.** 앞 순서 재계획 로봇이 뒤 순서 고정 로봇의 **작업 구간**을
모르고 지나가는 일이 없어진다.

### 결정 6. 로봇마다 "다시 계획을 시작하는 시각"과 "남은 작업 시간"을 정한다

지금은 모든 재계획 로봇이 **T에서** 출발한다. 앞으로는 상태에 따라 다르다.

| 상태 (T 기준) | 다시 계획을 시작하는 시각 | A\*에 넘기는 작업 시간 |
|---|---|---|
| 이동 중 (T < start) | T | **S** (도착하면 작업해야 함) |
| 작업 중 (start ≤ T < end) | **end** (작업이 끝나야 움직임) | **0** (이미 하고 있음) |
| 주차 중 (end ≤ T) | T | **0** (이미 끝남) |

그리고 경로를 이어붙일 때(`splice_paths`)도 이 시각을 쓴다. 작업 중인 로봇은 옛 경로의 **end 이전
부분(남은 작업 포함)을 그대로** 두고, end부터 새 경로를 붙인다.

### 결정 7. A\* 도착 판정에 작업 시간을 넣는다

```
지금:     목적지에 t_a에 닿았고, t_a > 목적지가 마지막으로 예약된 시각  → 도착
앞으로:   위 조건 + t_a + 작업 시간 ≤ max_timestep                      → 도착
          도착하면 경로 끝에 작업 시간만큼 머무는 칸을 붙여서 돌려준다
```

**왜 조건이 하나만 늘어나나?** 지금도 A\*는 "도착 후 max_timestep까지 목적지가 비어 있어야" 도착으로
인정한다(Tail 때문). 작업 구간은 그 안에 들어 있으니, 작업 중에 누가 목적지를 지나갈 일은 **이미
막혀 있다.** 새로 필요한 건 "작업이 **시간 한도 안에 끝나는가**"뿐이다.

바로 실패하는 조건(91-94줄)도 같이 바뀐다: 가장 빨리 도착해도 `마지막 예약 시각 + 1 + 작업 시간 >
max_timestep`이면 탐색 없이 실패.

A\*는 여전히 "로봇이 몇 대인지"를 모른다. 작업 시간은 "도착하면 몇 스텝 머물러야 하나"라는 **이
로봇 한 대의 조건**이라서 A\*에 넘기는 게 자연스럽다.

### 결정 8. 아이디어 3도 작업 시간을 반영한다

- **3-1 도달성 검사**: "가장 빨리 도착 + 작업 시간 ≤ max_timestep"인지 본다. A\* 규칙과 똑같아야
  "결과를 안 바꾸고 시간만 아낀다"가 유지된다.
- **3-2 구조 후보**: 바꿀 게 없다. 최단 경로와 부딪히는 칸의 주인을 찾는데, 작업 중인 로봇의 칸도
  (결정 5 덕분에) 장부에 있으니 **그대로 후보가 된다.** 불려도 작업이 끝난 뒤에만 움직이므로(결정 4)
  안전하다.

### 결정 9. 재계획 후 새 작업 일정을 계산하는 규칙

```
T에 아직 도착 전(이동 중)이던 로봇:  새 경로에서 다시 계산
                                    end = 경로 끝 시각, start = end − 작업 시간
나머지(작업 중, 주차 중):            옛 일정 그대로 (이미 도착했으니 안 바뀐다)
```

이동 중이면서 다시 계획되지 않은 로봇(고정 로봇)은 경로가 그대로라서, 다시 계산해도 같은 값이 나온다.
그래서 규칙이 "이동 중이면 다시 계산"으로 간단해진다.

### 결정 10. 함수 모양(API)

> **구현하며 바꾼 점 (2026-11-17)**: 근무표 함수들은 `PrioritizedPlanner` 안이 아니라 별도 파일
> `core/include/mapf/task_schedule.hpp`에 두었다. 근무표는 "누가 언제 작업하나"만 다루는 독립된
> 개념이라 따로 두면 읽기 쉽고, 플래너 없이 따로 테스트할 수 있다. 경로 하나에서 작업 구간을 읽는
> `window_from_path`와 상태 판정 `task_state_at`도 같이 두었다. `window_from_path`는 경로 끝의
> (작업 시간 + 1)개 칸이 전부 목적지인지 확인하고, 아니면 에러를 낸다(결정 3의 실수를 막는 **보조** 안전장치).
> **한계**: 구조 로봇으로 불렸지만 실제로는 안 움직인 로봇(헛부탁)의 경로는 끝까지 전부 목적지라 검사를
> 통과하고 작업 구간을 틀리게 읽는다. 그래서 `window_from_path`/`schedule_from_plan`은 **처음 계획 결과에만**
> 쓰고, 재계획 결과에는 반드시 `update_schedule`을 쓴다. `update_schedule`은 이미 도착한 로봇의 경로를
> 다시 읽지 않으므로 이 경우도 안전하다(테스트 `UpdateScheduleKeepsRescuedAgentThatDidNotMove`).

```cpp

TaskState    task_state_at(const TaskWindow& window, int t);         // 이동 중 / 작업 중 / 주차 중
TaskWindow   window_from_path(const Agent& agent, const Path& path);  // end = 경로 끝, start = end − 작업 시간

// 처음 계획의 결과에서 작업 일정을 만든다
TaskSchedule schedule_from_plan(const std::vector<Agent>& agents, const PlanResult& paths);

// 재계획 — 작업 일정을 받는 새 버전
std::optional<ReplanResult> replan(agents, previous_paths, previous_schedule, new_obstacles, current_time);
std::optional<PlanResult>   full_replan(agents, previous_paths, previous_schedule, new_obstacles, current_time);

// 재계획 — 지금 버전(작업 일정 없이). 모든 로봇의 작업 시간이 0일 때만 쓸 수 있다.
// 작업 시간이 있는 로봇이 있으면 std::invalid_argument를 던진다.
std::optional<ReplanResult> replan(agents, previous_paths, new_obstacles, current_time);
std::optional<PlanResult>   full_replan(agents, previous_paths, new_obstacles, current_time);

TaskSchedule update_schedule(agents, previous_schedule, new_paths, current_time);

struct ReplanResult {
    ...(지금과 같음)...
    TaskSchedule schedule;   // 새로 추가: 재계획 후의 작업 일정
};
```

**왜 옛 버전은 작업 시간이 있으면 에러를 내나?** 옛 버전은 작업 일정을 모른다. 경로에서 추측하면
결정 3에서 본 것처럼 **조용히 틀린다.** 조용히 틀리는 것보다 바로 에러가 나는 게 안전하다.

## 17.5 예시로 따라가기 — K가 작업 중일 때

16장과 같은 지도, 같은 로봇, 같은 사건(t=3에 (4,2)에 장애물)이다. 설정은 고정 먼저 + 아이디어 3.
**K의 작업 시간만 바꿔 본다.** K는 t0에 도착해 있었다.

### 경우 1: K의 작업 시간 = 2 → t2에 작업 끝, T=3에는 **주차 중**

작업 일정: K [0, 2]. T=3 ≥ 2 → 주차 중.
**16장과 완전히 같다.** K는 t5에 (4,0)으로 비켰다가 t6에 돌아오고, W는 t8에 도착한다.

### 경우 2: K의 작업 시간 = 8 → t8까지 작업, T=3에는 **작업 중**

작업 일정: K [0, 8]. T=3 < 8 → 작업 중. **t8부터** 움직일 수 있다.

**Tier 0** (순서 K, Z → W)
1. 장부: 장애물 (4,2) t3~, **K의 남은 작업 (4,1) t3~t8** (결정 5), K 옛 경로 전체(작업 + Tail), Z.
2. W의 A\*: (4,1)은 K가 영원히 차지(Tail) → 실패. 16장과 같다.
3. 3-2: 최단 경로의 (4,1)t5 → 주인 K → K를 부른다.

**Tier 1** (순서 Z → W → K)
1. 장부: 장애물, **K의 남은 작업 (4,1) t3~t8** ← 여기가 16장과 다르다. K는 working인데도 작업 구간은 적혀 있다.
2. Z 옛 경로.
3. W의 A\*: (4,1)이 t8까지 막혀 있다. 다른 길은 없으니 **기다린다.** 가장 빨리 (4,1)에 들어가는 시각은
   **t9**다. → (6,2)에 **t12** 도착.
4. K의 A\*: 결정 6에 따라 **t8에 (4,1)에서** 출발하고, 작업 시간 0. W가 t9에 (4,1)로 들어오니 K는 t9에
   비켜야 한다. (4,0)으로 비켰다가 W가 지나간 뒤 **t10**에 돌아온다.
5. K 경로 이어붙이기: 옛 경로의 t0~t7(작업 포함) + 새 경로 (4,1)t8 (4,0)t9 (4,1)t10.

| | 경우 1 (주차 중) | 경우 2 (작업 중) |
|---|---|---|
| K가 움직이는 시각 | t5 | **t9** (작업이 끝난 뒤) |
| W 도착 | t8 | **t12** (K의 작업을 기다림) |
| 작업 도중 이동? | 해당 없음 | **없음** ✔ |

> 위 시각들은 설계대로 손으로 계산한 **예상값**이다. 구현한 뒤 테스트로 확인한다(17.8).
> W가 (3,2)와 (3,1) 중 어디서 기다리는지는 A\*의 동점 처리에 따라 달라질 수 있다. 도착 시각 t12는
> 유일한 최단 시각이라 달라지지 않는다.

### 만약 결정 5가 없다면 (틀린 설계)

Tier 1에서 W의 A\*는 K의 작업을 모르고 t5에 (4,1)을 지나간다. 그다음 K를 등록할 때 K의 남은 작업
(4,1)t5와 겹쳐 **거절** → 실패. 이 실패에는 "누가 막았는지" 정보도 없어서 안전망으로 간다.

5. 작업 중인 로봇이 구조되면 막힌 로봇보다 뒤에 계획되는데, 먼저 안 적으면 막힌 로봇의 A\*가 작업을 모르고 그 칸을 지나간다. 16장 Tier 1에서 W가 t5에 (4,1)을 지나가고, K의 남은 작업과 겹쳐 등록이 거절되어 실패한다.
6. 이동 중: T에서, 작업 시간 S. 작업 중: end에서, 0. 주차 중: T에서, 0.
7. A\*는 이미 "도착 후 max_timestep까지 목적지가 비어 있어야" 도착으로 인정한다. 작업 구간은 그 안에 있으니 이미 보호된다. 남은 건 작업이 max_timestep 안에 끝나는지뿐이다.
8. (4,1)이 K의 남은 작업 때문에 t8까지 막혀 있고 다른 길이 없다. 가장 빨리 t9에 (4,1)에 들어가고, (5,1)t10 (5,2)t11 (6,2)t12.
9. 작업 일정을 모르면 경로에서 추측해야 하는데, 그러면 조용히 틀릴 수 있다. 조용히 틀리는 것보다 바로 에러가 나는 게 안전하다.

## 17.12 자주 묻는 질문

### Q1. Tail을 max_timestep까지가 아니라 "도착 + 작업 시간"까지만 예약하면 안 되나?

**안 된다.** 장부 예약은 "이 로봇이 **실제로** 그 칸에 있다"는 뜻이다. 작업이 끝나도 다음 일이 없으면 로봇은
그 자리에 그대로 서 있다. 예약을 지우면 다른 로봇의 A\*가 그 칸을 빈 칸으로 보고 지나가는 길을 고르고,
실제로는 충돌한다.

```
K: t0 도착, 작업 5 → 예약을 t0~t5까지만 함
→ t6부터 (4,1)이 장부에서 빈 칸
→ W의 A*가 t7에 (4,1) 통과
→ K는 실제로 아직 (4,1)에 서 있음 → 충돌
```

이 질문이 원하는 두 가지는 다른 방법으로 이룬다.

| 원하는 것 | 방법 |
|---|---|
| 작업이 끝나면 비켜 줄 수 있어야 한다 | 예약은 그대로 두고, "비켜 줄 수 있는 상태"를 **작업 일정(결정 3)**으로 따로 표시한다. 구조 로봇으로 불리면 비켜 준다(결정 4) |
| 작업이 끝나면 다음 일을 받아야 한다 | 새 일이 오는 순간 그 로봇을 새 목적지로 다시 계획한다. 옛 Tail은 새 경로로 바뀐다. lifelong 확장이라 이번 범위 밖(17.10) |

즉 Tail의 진짜 뜻은 "영원히"가 아니라 **"새 지시가 올 때까지 여기 있음"**이다.

참고: MAPF에는 "도착하면 사라진다"(*disappear at target*)는 모델도 있지만, 창고 로봇은 사라지지 않으므로 쓰지 않는다.

### Q2. 결정 3·4·5는 어떻게 이어지나?

```
결정 3 (근무표)    : 누가 지금 작업 중인지 정확히 안다
     ↓
결정 4 (약속)      : 작업 중인 로봇은 끝난 뒤에만 비켜 준다
     ↓
결정 5 (미리 적기) : 그 약속을 장부에 먼저 적어서 다른 로봇이 지키게 한다
```

결정 5가 필요한 이유는 코드 규칙 하나 때문이다. **구조 로봇(working_ids)은 옛 경로를 장부에 적지 않고, 자기
차례에 A\*로 새 길을 찾을 때 비로소 적는다.** 그래서 구조 로봇이 된 작업 중 로봇은, 먼저 적어 두지 않으면
앞 차례 로봇들 눈에 안 보인다.

### Q3. 도착 t2, 작업 시간 3이면 왜 t6이 아니라 t5부터 움직일 수 있나?

**"t5부터 움직일 수 있다" = t5에 출발한다**는 뜻이다. 옆 칸에 도착하는 건 t6이다.

```
시각:     t2        t3        t4        t5        t6
          │         │         │         │         │
위치:   (2,0)     (2,0)     (2,0)     (2,0)     옆 칸
          ├─ 작업1 ─┼─ 작업2 ─┼─ 작업3 ─┼─ 이동 ──┤
          ↑                             ↑
        도착                          작업 끝 = 출발
```

- **시각(t2, t3, …)은 점**이다. 경로의 각 칸 `(x, y, t)`는 "그 순간 어디 있나"를 나타낸다.
- **스텝은 점과 점 사이의 구간**이다. 한 스텝 동안 한 칸 이동하거나, 제자리에 있거나, 작업 한 단위를 한다.
- 작업 시간 3 = 구간 3개(t2→t3, t3→t4, t4→t5). t5에 끝나고, 바로 다음 구간 t5→t6에 출발할 수 있다.
- 그래서 경로에 (2,0)이 t2~t5로 **4번**(점) 나오지만 작업은 **3스텝**(구간)이다. 울타리 기둥 4개 사이의 칸이 3개인 것과 같다.

"도착 + 작업 시간 + 1"에 출발하게 하면 작업 시간 0인 로봇도 도착 후 한 스텝을 쉬어야 해서, "작업 시간 0이면
예전과 똑같다"는 약속이 깨진다.
