# 30. 우리 방법이 실패하는 경우 찾기 — 어떤 경우가 있고, 고칠 수 있나

> 2026-11-20, 사용자 요청: "성공률이 높다지만 100%는 아니다. 재계획에 실패하는 테스트 케이스를 찾아 어떤 경우가 있는지 알아내고,
> 해결할 수 있으면 해결하자." 이 장은 **찾기·원인 분석**까지 했고, **해결 방법은 제안만** 한다(결정 필요, 30.5).

---

## 30.0 세 줄 요약

1. 실패는 **좁은 통로 + 로봇 150~200대**에서만 생긴다(400개 중 0~5개). 넓은 맵, 로봇 100대 이하에서는 0이다.
2. 원인은 두 가지뿐이었다: **(가) 넓히기를 한 번만 해서 모자람**(Tier 2~3이면 풀림), **(나) PP의 우선순위 순서**(순서만 바꾸면 풀림).
   "길이 정말 끊김"이나 "시간 상한"은 한 건도 없었다.
3. 고치는 방법 두 가지를 제안한다: **Tier를 2로**, 그리고 **전체 재계획까지 실패했을 때만 순서를 바꿔 다시 시도**. 이러면 평소 속도는
   그대로이면서 "전체 재계획도 못 푸는 경우"의 대부분을 풀 수 있다(30.5).

## 30.1 실패를 두 종류로 나눈다

| 종류 | 뜻 | 성공률에 |
|---|---|---|
| **A. 안전망 사용** | Tier 0·Tier 1이 실패해서 전체 재계획으로 풀었음 | 성공으로 셈. 단 "선택적"으로 못 풀었고 느림 |
| **B. 완전 실패** | 전체 재계획까지 실패 | 실패. 우리 방법은 안전망 때문에 **전체 재계획이 실패할 때만** 실패한다 |

## 30.2 어떻게 찾았나 (도구)

1. 벤치마크에 `--dump-failures DIR` 옵션을 추가했다. A·B에 해당하는 시나리오를 `DIR/<지도>_<로봇 수>_<번호>.json`으로 저장한다
   (지도, 로봇의 출발·목적지·작업 시간, 처음 경로, 장애물, 지금 시각). 결과에는 영향 없음(기본 7개 설정 칸마다 같음 확인).
2. 저장한 18개: `tools/results/v7_failures/`.
3. `python tools/analyze_failures.py tools/results/v7_failures/*` — 같은 장면을 파이썬으로 그대로 다시 돌려서 아래 6가지를 확인한다.

| 확인 | 질문 |
|---|---|
| ① 재현 | 같은 결과가 나오나 → **18개 모두 재현** |
| ② 길 끊김 | 다른 로봇이 하나도 없어도 목적지에 못 가나(BFS) → **0건** |
| ③ 더 넓히기 | Tier를 2·3·5로 늘리면 풀리나 |
| ④ 비켜 달라기 | request_yield를 켜면 풀리나 → **0건** |
| ⑤ 순서 | 전체 재계획을 무작위 우선순위로 60번 → 몇 번 풀리나 |
| ⑥ 시간 상한 | max_timestep 256 → 512로 늘리면 → **0건** |
| ⑦ 작업 중 로봇 | 막힌 로봇의 최단 길 위에 작업 중인(못 움직이는) 로봇이 서 있나 |

### 원인 정리 (쉬운 말)

- **(가) 넓히기가 한 번으로 모자람 — 4건.** Tier 1에서 부른 구조 로봇이 또 다른 로봇에게 막히는 경우다. 한 번 더 넓히면(Tier 2, 한 건은 Tier 3) 풀린다.
  그중 1건(#31)은 **전체 재계획도 못 푸는 경우인데 우리 방법이 Tier 3으로 푼다.**
- **(나) PP의 우선순위 순서 — 나머지 대부분.** PP는 정해진 순서대로 한 대씩 계획한다. 앞 순서 로봇이 좁은 통로를 먼저 차지해 버리면 뒤 로봇이 갈 곳이 없다.
  **순서만 바꾸면 풀린다**: 모든 케이스에서 전체 재계획을 무작위 순서로 돌리면 최소 1/60 이상 풀렸다 → **"원래 불가능한 문제"는 하나도 없었다.**
  우리 방법도 다시 계획할 로봇들의 순서만 바꾸면 18건 중 15건을 안전망 없이 푼다(그중 **완전 실패 B 8건 중 6건**).
- **원인이 아니었던 것**: 길이 정말 끊김(0건), 시간 상한(0건), 비켜 달라기 부족(0건).
- **작업 중인 로봇**: 작업 시간을 켠 케이스에서는 막힌 로봇의 길 위에 작업 중인 로봇이 서 있는 경우가 많다. 하지만 순서를 바꾸면 대부분 풀리므로
  "작업 중 로봇 때문에 절대 못 푸는" 경우는 이번 18건에는 없었다.
- **남은 3건**(standing 200대 #34, #5 두 개): 순서를 20번 바꿔도 우리 방법으로는 안 풀린다. #34는 전체 재계획이 풀어서(A) 문제없고,
  #5는 전체 재계획도 무작위 순서로 2~6/60만 풀리는 아주 빡빡한 경우다.

## 30.4 왜 "순서 바꿔 다시"를 항상 하면 안 되나 — 시간

실패하는 시도는 느리다. A\*가 갈 수 있는 곳을 다 뒤져 보고 실패하기 때문이다. 200대에서 실패하는 시도 한 번이 **0.2~0.9초**다
(전체 재계획 중앙값 0.25초보다 느림). 그리고 처음 성공하는 순서가 나올 때까지 최대 4번 실패했다. 그래서 "안전망 전에 순서를 바꿔 여러 번"
하면 이런 드문 경우에 몇 초가 걸릴 수 있다 — 빠른 재계획이라는 장점을 해친다.

## 30.5 해결 제안 (⚠ 결정 필요 — 아직 구현 안 함)

| 제안 | 무엇을 | 효과(18건 기준) | 평소 속도 | 비고 |
|---|---|---|---|---|
| **① Tier 1 → 2** | 넓히기를 한 번 더 | A 3건이 안전망 없이 풀림 | 거의 그대로(Tier 1이 실패할 때만 한 번 더) | 설정값만 바꿈 |
| **② 마지막에 순서 바꿔 다시** | **전체 재계획(안전망)까지 실패했을 때만**, 다시 계획할 로봇 순서를 바꿔 우리 방법을 최대 K번(예: 5번) 더, 그래도 안 되면 전체 재계획도 순서를 바꿔 K번 | B 8건 중 6건이 우리 방법으로 성공(남은 2건은 전체 재계획 순서 바꾸기로 일부 가능) | **그대로**(원래 실패하던 경우에만 시간을 더 씀) | 무작위 재시작은 **이미 알려진 기법**(PP with random restarts, Bennewitz 2001 — Morag 2023도 사용). 새롭다고 주장하지 않는다. 시드 고정으로 결과 재현 가능 |
| (비추천) 안전망 **전에** 순서 바꿔 다시 | | A도 대부분 안전망 없이 | 드문 경우 몇 초 | 30.4 |

**① + ②를 하면**: 평소 속도는 지금과 같고, "전체 재계획 이상" 보장은 그대로이면서 **전체 재계획이 실패하는 경우의 상당수를 우리가 푼다**
(성공률이 전체 재계획보다 **높아진다**). 다만 공정하게 하려면 비교 기준에도 "전체 재계획 + 무작위 재시작"을 같이 보고해야 한다.

**정해야 할 것**
1. ①(Tier 2)을 할까? — 추천: 한다.
2. ②(전체 재계획까지 실패했을 때만 순서 바꿔 다시)를 할까? 한다면 K는? — 추천: 한다, K=5.
3. 두 개 다 지금까지처럼 **스위치(기본 꺼짐) → 테스트 → 벤치마크로 "꺼짐 = 같음" 확인 → 켜고 전체 실험 다시**의 순서로 한다.
