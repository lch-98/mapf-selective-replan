## 10.0 결론 먼저

| 질문 | 답 |
|---|---|
| Space-Time A*는 기존 알고리즘과 같은가? | **같다.** Silver(2005)의 Cooperative A*(CA*)와 같은 구조(시공간 탐색 + 예약 테이블 + 대기 동작)이고, 도착 판정(목적지에 끝까지 머물 수 있을 때만 도착)도 우선순위 기반 계획에서 쓰는 방식과 같다. 다른 점은 휴리스틱이 맨해튼 거리라는 것뿐(HCA*는 실제 최단거리 휴리스틱). |
| `PBS` 클래스는 PBS(Ma et al., 2019)와 같은가? | **다르다.** 이름은 PBS지만 실제로는 **고정 우선순위 계획(Prioritized Planning, PP)**이다. 진짜 PBS는 우선순위 순서 자체를 탐색하는데, 이 코드는 `agents` 벡터 순서를 절대 바꾸지 않는다. |
| 결과 경로가 충돌하는 논리 오류가 있는가? | **현재 코드에서는 찾지 못했다.** 모든 경로가 `register_path` 한 곳을 반드시 통과하고, 거기서 모든 로봇 쌍의 칸·이동·도착 후 머묾이 빠짐없이 검사된다(10.3절의 증명). 테스트 47개, 벤치마크 결과 1197개 전수 검사, GUI 30대 검사 모두 0건. |
| 설계 문제는 있는가? | **있다.** 안전성(충돌)이 아니라 **성공률·속도**를 깎는 문제다. 가장 큰 것은 10.5절의 **"고정 로봇과 재계획 로봇을 우선순위 순서로 섞어서 등록"**하는 구조 — 실험상 Tier 0 실패의 **99% 이상**이 이것 때문이었다. |

## 10.1 Space-Time A* — 기존 알고리즘과 비교

### 기준 알고리즘: Cooperative A* (Silver, 2005)

로봇마다 (x, y, 시간) 3차원 공간에서 A*를 돌리고, 앞서 계획된 로봇의 경로를
**예약 테이블**에 기록해 두어 뒤 로봇이 피하게 한다. HCA*는 여기에 "다른 로봇을
무시한 실제 최단거리"를 휴리스틱으로 쓰고, WHCA*는 탐색 시간 창을 제한한다.

### 우리 코드와 비교

| 요소 | Cooperative A* | 우리 코드 | 같은가 |
|---|---|---|---|
| 탐색 상태 | (x, y, t) | `SpaceTimeCell{x, y, t}` | ✅ |
| 동작 | 상하좌우 이동 + 대기, 모두 비용 1 | `Map::neighbors`(대기 포함), g += 1 | ✅ |
| 칸 충돌 | 예약된 (칸, 시각)에 못 들어감 | `is_occupied(next, t+1)` | ✅ |
| 자리 맞바꾸기 충돌 | 반대 방향 동시 이동 금지 | `is_edge_occupied` (양방향 기록) | ✅ |
| 도착 판정 | 도착 후 목적지에 머물 수 있어야 함* | 목적지가 마지막으로 예약된 시각보다 뒤에 도착해야 인정 | ✅ |
| 휴리스틱 | CA*: 맨해튼, HCA*: 실제 최단거리 | 맨해튼 | CA*와 같음 |
| 탐색 한계 | 구현마다 다름 | `max_timestep`(기본 256) | ✅ |

\* 도착 후 계속 머문다고 보고 예약하는 방식에서는, 목적지에 늦게라도 머물 수 있는
시각 이후에 도착해야 한다. 2026-09-13에 이 조건을 넣기 전에는 "도착하자마자 끝"이라
등록 단계에서 실패했다([PROGRESS.md](PROGRESS.md) 참고).

### 정확성 확인 (한 줄씩 따져본 결과)

1. **최단 도착 시각을 찾는가?** 모든 동작의 비용이 1이고 시간도 1씩 늘어서,
   어떤 노드든 **g = t − 시작 시각**이다. 같은 (x, y, t)는 어떤 길로 와도 비용이
   같으므로, `visited`로 두 번 펼치지 않아도 손해가 없다. 맨해튼 거리는 대기
   동작(비용 1, h 그대로)까지 포함해 **일관적(consistent)**이라, 꺼내지는 노드의 f가
   줄어들지 않는다. 그래서 **처음 꺼낸 "머물 수 있는 도착 노드"가 가장 이른 도착**이다. ✅
2. **끝나는가?** 상태 수가 칸 수 × (max_timestep − 시작 시각 + 1)로 유한하고, 각
   상태는 한 번만 펼친다. ✅
3. **시작 칸은 검사하지 않는다.** 설계상 의도이며, `register_path`가 대신 잡는다. ✅
4. **목적지가 끝까지 막혀 있으면 바로 실패한다.** 탐색 없이 끝내서 헛탐색을 막는다. ✅

### 약점 (오류는 아니지만 성능·진단에 영향)

| 약점 | 영향 | 일반적인 해결책 |
|---|---|---|
| **맨해튼 휴리스틱** | 벽이 많은 맵(corridor)에서 실제 거리보다 많이 작아 불필요한 노드를 많이 펼친다. | 목적지에서 BFS로 구한 실제 최단거리(HCA* 방식). 한 번 계산해 재사용. |
| **경로가 없을 때 전부 뒤짐** | 칸 수 × 시간(64×64×256 ≈ 100만 상태)을 다 펼친 뒤에야 실패. 대규모 실험에서 전체 재계획이 수 초 걸린 원인으로 **추정**(아직 측정 안 함). | SIPP(안전 구간 탐색), 시간 창 제한(WHCA*), 사전 도달성 검사. |
| **노드마다 `shared_ptr` 할당** | 메모리 할당 비용이 크다. | 노드 풀/배열. |
| **동점일 때 순서 임의** | f가 같은 노드 중 아무거나 꺼낸다. 결과는 최적이지만 탐색량이 늘 수 있다. | 동점이면 g가 큰 쪽 우선. |
| **`blocked_attempts`가 탐색 중 막힌 모든 칸** | 크게 불어나고 중복도 많다. Tier 1이 이걸로 "막은 로봇"을 고르므로, 경로와 무관한 로봇까지 끌려올 수 있다(10.5절 문제 3). | 최단 경로상 충돌만 원인으로 보기. |

## 10.2 `PBS` 클래스 — 이름과 실제가 다르다

### 기준 알고리즘: PBS (Ma, Harabor, Stuckey, Li, Koenig, AAAI 2019)

고정된 우선순위 순서 하나를 정해 두는 대신, **가능한 (부분) 우선순위 순서의 공간을
충돌이 날 때마다 체계적으로 탐색**한다. 두 로봇이 부딪히면 "A가 B보다 먼저" /
"B가 A보다 먼저" 두 갈래로 나눠 각각 다시 계획해 보는 식이다. 같은 논문이 고정 순서
방식(PP)의 완전성·최적성 한계도 이론적으로 다룬다.

### 우리 코드

`PBS::plan()`은 `agents` 벡터 **순서대로 한 대씩** A*로 계획하고 등록한다. 한 대라도
실패하면 전체 실패(`nullopt`). 순서를 바꿔 다시 시도하는 부분이 없다.

| | 진짜 PBS | 우리 `PBS::plan()` |
|---|---|---|
| 우선순위 | 탐색 대상(바뀜) | `agents` 순서로 고정 |
| 충돌이 나면 | 순서를 바꾼 두 갈래를 시도 | 그 로봇에서 실패로 끝 |
| 알고리즘 분류 | 우선순위 탐색 | **고정 우선순위 계획(PP)** = CA*를 로봇 수만큼 반복 |

**결론: 알고리즘 자체는 교과서적인 PP로 정확하게 구현되어 있다. 다만 이름이
PBS라서, 논문이나 발표에서 "PBS를 썼다"고 하면 틀린 설명이 된다.** "Prioritized
Planning(고정 순서) 위에 선택적 재계획을 얹었다"고 설명해야 한다.

이 차이가 실제로 드러나는 곳: 초기 계획 실패, Tier 1의 효과 제한(10.5절 문제 2),
그리고 전체 재계획이 선택적 재계획보다 오히려 못 푸는 경우(trial 36 분석) 모두 **순서가
고정되어 있기 때문**이다.

## 10.3 안전성 증명 — 결과 경로가 충돌하지 않는 이유

결과로 나가는 모든 경로는 반드시 `register_path`를 통과한다(A*로 찾은 경로든, 옛 경로를
그대로 쓰는 경우든). 로봇 i가 먼저, j가 나중에 등록된다고 할 때, j를 등록하는 순간
테이블에는 i의 **경로 칸 + 경로 이동 + 도착 후 머묾**이 모두 들어 있다.

| 충돌 종류 | 누가 잡는가 |
|---|---|
| j의 경로 칸 ↔ i의 경로 칸 / i의 머묾 | j 칸 등록 시 `reserve_if_unowned` |
| j의 머묾 ↔ i의 경로 칸 / i의 머묾 | j 머묾 등록 시 `reserve_if_unowned` |
| j의 이동 ↔ i의 이동 (자리 맞바꾸기) | j 이동 등록 시 `is_edge_occupied` (i가 양방향 기록) |
| 머묾 중인 로봇과 자리 맞바꾸기 | 머무는 로봇은 움직이지 않으므로 칸 충돌로 환원 → 위에서 잡힘 |
| 새 장애물 | owner −1로 먼저 예약 → 어떤 로봇도 `reserve_if_unowned` 통과 불가 |

모든 쌍(i < j)에 대해 이 표가 빠짐없이 적용되므로, **등록에 성공한 결과에는
max_timestep 안에서 칸 충돌·자리 맞바꾸기가 없다.** max_timestep 이후에는 모든 로봇이
서로 다른 목적지에 머문다(같은 목적지면 머묾 등록에서 거절됨).

이 증명은 실험과도 맞는다: 벤치마크 결과 1197개 전수 검사, GUI 30대로 경로 449개 검사
(여러 번 클릭 포함) 모두 충돌 0건.

> 이 성질은 과거 두 번 깨졌었다 — 옛 경로 등록 때 이동을 검사하지 않던 swap 버그
> (`cf22720`), 이어붙인 경로의 시각이 비던 버그(`154fcba`). 둘 다 "`register_path`가
> 유일한 관문"이라는 원칙에서 벗어난 경로가 있었기 때문이다. **앞으로 전략적 재계획
> 층을 만들 때도 결과 경로는 반드시 이 관문을 통과하게 해야 한다.**

## 10.4 예약 테이블 — 의미 확인

- 칸 예약은 **주인(로봇 id)**을 기록한다. 장애물은 −1. `get_owner`로 원인 추적 가능. ✅
- 이동 예약은 **주인 없이** 양방향으로 기록한다. 대기도 (a→a)로 기록되지만, 같은 칸에
  두 로봇이 대기하면 이미 칸 충돌이라 문제없다. ✅
- 약점: 이동 예약에 주인이 없어서, **자리 맞바꾸기 때문에 막힌 경우는 원인 로봇을 알 수
  없다**(Tier 1이 추적 못 함).
- `register_path`가 중간에 실패하면 그때까지 쓴 예약이 테이블에 남는다. 지금은 실패하면
  곧바로 테이블을 비우고 다시 시작하므로 무해하지만, 테이블을 재사용하는 설계로 바꾸면
  문제가 된다.

## 10.5 선택적 재계획(`replan`) — 설계 문제

### 문제 1 (가장 큼): 고정 로봇과 재계획 로봇을 우선순위 순서로 섞어서 등록한다

`try_replan_set`은 `agents` 순서대로 돌면서, 재계획 대상(working)이면 A*를, 아니면 옛
경로 등록을 한다. 그래서 **앞 순서의 재계획 로봇은 뒤 순서 고정 로봇의 옛 경로를 모른 채**
경로를 찾는다. 모르고 그 위를 지나가면, 나중에 고정 로봇 등록이 거절되고 Tier 0이 실패한다.

```
순서: [W(재계획), N(고정)]
W의 A*: N은 아직 등록 전 → N의 옛 경로를 그냥 지나감
N 등록: W와 부딪힘 → 거절 → Tier 0 실패 → N을 불러와 Tier 1
```

**실험 결과**(Tier를 올린 원인을 임시 계측으로 기록):

| 설정 | 원인: 고정 로봇 등록 거절 | 원인: A* 실패 |
|---|---|---|
| 기본 (32×32) | 95 / 95건 | 0건 |
| 대규모 (64×64), 추적 단계 1 | 255 / 257건 | 2건 |
| 대규모, 추적 단계 3 | 596 / 600건 | 4건 |

**Tier 0 실패의 99% 이상이 이 구조 때문이다.** 고정 로봇들의 옛 경로는 이전 계획에서 서로
충돌이 없었고 새 장애물과도 겹치지 않으므로, **이들을 먼저 전부 등록**하고 재계획 로봇이
그걸 피해서 찾게 하면 "고정 로봇 등록 거절"은 원리적으로 한 번도 일어나지 않는다. 일부만
다시 계획하는 기존 방식(MAPF-LNS 계열)도 이웃 밖 로봇의 경로를 고정 제약으로 두고 이웃만
다시 계획한다.

- 대가: 재계획 로봇이 "뒤 순서 로봇보다 우선한다"는 규칙이 사라진다(모든 고정 로봇을
  피해야 함). 대신 선택적 재계획의 목적(안 건드린 로봇은 안 바뀐다)과 더 잘 맞는다.
- 주의: 성공률이 **반드시** 오른다는 보장은 없다(한 로봇이 고정 로봇을 피해 다른 길을
  고르면 다음 재계획 로봇을 막을 수도 있다). **실험으로 확인해야 한다.**

### 문제 2: 순서가 고정되어 있어 "구조 로봇"이 비켜주지 못할 수 있다

- A* 실패로 원인을 추적할 때 찾는 로봇은 **구조적으로 항상 막힌 로봇보다 앞 순서**다(A*
  실행 시점의 테이블에는 앞 순서 로봇만 있으므로). 불러와도 막힌 로봇보다 **먼저**, 그 로봇을
  모른 채 다시 계획하므로 같은 길을 고를 가능성이 크다.
- 다만 위 실험처럼 이 경로는 **실제로는 드물다**(1% 미만). 지금 병목은 문제 1이다.
- 고정 로봇 등록 거절로 불러오는 로봇은 뒤 순서라, 다시 계획할 때 앞 로봇을 알고 피할 수
  있다. 그런데도 다음 시도 성공률이 20~54%에 그친다. 처음엔 "연쇄" 때문이라고 추정했지만,
  [11장](11_rescue_robot_verification.md)에서 측정해 보니 연쇄는 약 18%였다. 약 75%는 첫 거절에서
  멈추는 구조 때문에 **원래 있던 충돌이 한 시도에 하나씩만 드러나는 "숨은 충돌"**이었다.

### 문제 3: "막은 로봇" 판정이 거칠다

`blocked_attempts`는 탐색 중 **한 번이라도 막힌 모든 칸**이라, 실제 경로와 무관한 먼 곳의
로봇까지 구조 대상이 될 수 있다. 자리 맞바꾸기로 막힌 경우는 원인 로봇을 못 찾는다(10.4절).

### 문제 4: 전체 재계획도 같은 고정 순서

안전망인 `full_replan`도 같은 순서로 전부 다시 계획한다. 그래서 trial 36처럼 **옛 경로를
유지하는 선택적 재계획은 풀고 전체 재계획은 못 푸는** 경우가 생긴다. 비교 기준으로서 "전체
재계획"이 PP 한 번이라는 점을 논문에서 밝혀야 한다.

### 정상 동작 확인 (문제 아님)

- 영향받는 로봇 판별(`path_hits_obstacle`): current_time 이후 위치만 본다. ✅
- 과거 구간 + 새 구간 이어붙이기(`splice_paths`): 빈 시각을 목적지 머묾으로 채운다. ✅
- 새 장애물은 current_time부터 max_timestep까지 예약, 주인 −1이라 원인 추적에서 제외. ✅
- Tier 한도에 도달하거나 더 불러올 로봇이 없으면 안전망으로 간다. ✅

## 10.6 전략적 재계획 층을 위한 시사점

우선순위(효과가 크고 확인이 쉬운 순):

1. **고정 로봇 먼저 등록(문제 1)** — Tier 0 실패의 99%를 차지하는 원인을 없앤다. 코드 수정이
   작고(`try_replan_set`의 등록 순서), 기존 벤치마크로 바로 효과를 잴 수 있다.
2. **재계획 로봇들 사이의 순서를 바꿀 수 있게(문제 2·4)** — 막힌 관계("A가 B 때문에 막힘")로
   A를 B보다 먼저 계획하게 한다. 작은 범위에서 진짜 PBS처럼 순서를 탐색하는 셈이다.
3. **원인 판정 정교화(문제 3)** — 막힌 칸 전체가 아니라 "다른 로봇을 무시한 최단 경로와
   부딪히는 로봇"을 원인으로(MAPF-LNS2의 충돌 기반 이웃 선택과 비교 필요).
4. **A* 가속** — 실제 최단거리 휴리스틱, 동점 처리, 실패 시 헛탐색 방지(SIPP 검토).
5. **이름 정리** — `PBS` → 예: `PrioritizedPlanner`. 논문 설명과 코드가 일치하도록.

그리고 어떤 층을 얹든 **결과 경로는 `register_path`를 통과**해야 한다(10.3절).

## 10.8 후속 질문과 답

### Q1. `PBS` 클래스는 사실 PP인가?

**그렇다.** `agents` 순서가 한 번도 바뀌지 않고 순서를 탐색하지도 않는다(10.2절).

### Q2. 구조 로봇도 고정된 순서대로 등록되지 않나? `std::find`로 찾는데 왜 우선순위가 올라가나?

**우선순위는 올라가지 않는다.** 이전 설명에서 "구조 로봇은 항상 우선순위가 높다"처럼
들렸다면 틀린 표현이었다. 정확히 말하면 다음과 같다.

- `try_replan_set`의 반복문은 늘 `for (const Agent& agent : agents)`, 즉 **원래 순서**대로
  돈다. 구조 로봇도 **자기 원래 자리 차례**에 처리된다.
- `std::find`는 "이 로봇이 `working_ids` 안에 있나?"만 확인한다. 결과는 **처리 방식**만
  바꾼다(있으면 A*로 다시 계획, 없으면 옛 경로 그대로 등록). **순서에는 아무 영향이 없다.**

그런데 구조 로봇이 막힌 로봇보다 **앞 순서인지 뒤 순서인지**는 어떻게 불려 왔는지에 따라
정해진다. 두 종류가 있다.

| 종류 | 언제 불려 오나 | 막힌 로봇과 비교한 순서 | 다시 계획하면 |
|---|---|---|---|
| (a) `out_blocked_owner` | 고정 로봇의 옛 경로 등록이 거절됨 | **뒤 순서**(우선순위 낮음) | 앞 로봇의 새 경로가 테이블에 있으니 **보고 피할 수 있다** |
| (b) `out_blocked` 칸의 주인 | 재계획 로봇의 A*가 실패함 | **항상 앞 순서**(우선순위 높음) | 막힌 로봇보다 먼저 계획하므로 그 로봇을 **모른 채** 같은 길을 고를 수 있다 |

**(a)의 예** — 순서 `[W(1번, 재계획), N(2번, 고정)]`

```
시도 1: W가 A* → N의 옛 경로를 모르고 지나감 → N 등록 거절 → N을 working에 추가
시도 2: W가 먼저 A* (그대로) → N 차례에 A* → 테이블에 W가 있으니 W를 피해 감 ✅
```

"구조 로봇이 우선순위가 낮으면 문제없다"는 직관이 **바로 이 경우에 맞다.** 그리고 실제
확장의 **99%가 이 경우**다(10.5절 실험).

**(b)의 예** — 순서 `[K(1번, 고정), W(2번, 재계획)]`

```
시도 1: K 옛 경로 등록 → W가 A*, K 때문에 길이 없음 → 막은 칸 주인 K를 working에 추가
시도 2: K가 먼저 A* (W는 아직 테이블에 없음) → K는 W를 모르고 다시 최단 경로 → 같은 길일 가능성 큼
        → W 다시 막힘 ❌
```

(b)에서 주인이 **항상 앞 순서**인 이유: W가 A*를 돌리는 순간 테이블에는 W보다 앞 순서
로봇(과 장애물)만 들어 있다. 그러니 막은 칸의 주인은 앞 순서일 수밖에 없다. 다만 실제로는
1% 미만으로 드물다.

**남은 궁금증 → 11장에서 확인함** — (a)의 N 자신은 다음 시도에서 거의 100% 성공한다. 그래도
다음 시도 전체 성공률이 낮은 건 주로 **숨은 충돌**(약 75%) 때문이고, "연쇄"는 약 18%뿐이었다.
처음 추정은 일부만 맞았다. 자세한 내용과 (b) 처리 아이디어는
[11장](11_rescue_robot_verification.md)에 있다.
