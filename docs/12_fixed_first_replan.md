## 12.1 무엇을 바꿨나

### 설정 하나 추가 (`prioritized_planner.hpp`)

```cpp
enum class ReplanOrder {
    kPriority,    // 원래 방식: agents 순서대로 고정/재계획 로봇을 섞어서 처리
    kFixedFirst,  // 고정 로봇 먼저 → 처음 영향받은 로봇 → 구조 로봇(불려 온 순서)
};
struct ReplanConfig {
    int max_escalation_tiers{1};
    ReplanOrder order{ReplanOrder::kPriority};  // 기본값은 원래 방식 그대로
};
```

기본값을 원래 방식으로 둬서, 기존 테스트·벤치마크·GUI는 **아무것도 바뀌지 않는다.**
두 방식을 같은 코드에서 골라 쓸 수 있어 논문의 비교 실험(ablation)에 그대로 쓸 수 있다.

### `try_replan_set`: 순서만 바꾸고 내용은 그대로

반복문을 돌기 전에 **처리 순서 목록(`order`)**을 만든다. 반복문 안(옛 경로 등록 / A\* 후
등록)은 한 줄도 안 바꿨다.

```
kPriority  : order = agents 순서 그대로
kFixedFirst: order = [고정 로봇들 (agents 순서)] + [working_ids 순서]
                      └ 옛 경로 등록, 거절 없음      └ 처음 영향받은 로봇 → 구조 로봇
```

- 고정 로봇의 옛 경로는 서로 원래 충돌이 없고 새 장애물과도 안 겹친다(겹쳤다면 재계획
  대상이다). 그래서 먼저 전부 등록해도 **거절되지 않는다.** 재계획 로봇은 이들을 모두 알고
  피해서 경로를 찾는다.
- 구조 로봇은 자기가 막은 로봇이 이미 `working_ids`에 있을 때 불려 오므로, **항상 그 로봇보다
  뒤에** 계획된다. 11장에서 확인한 "(a)가 잘 되는 이유"를 모든 구조 로봇에 적용한 것이다.
- 안전망(`full_replan`)은 바꾸지 않았다(항상 `agents` 순서). 비교 기준이 흔들리지 않게 하려는 것이다.
- 결과 경로는 여전히 전부 `register_path`를 통과한다(10.3절의 안전성 조건 유지).

### 테스트 2개 추가 (`tests/test_prioritized_planner.cpp`)

| 테스트 | 확인하는 것 |
|---|---|
| `FixedFirstKeepsUnchangedAgentAndDetoursWorkingAgentAtTier0` | 원래 방식이 Tier 1로 푸는 시나리오를 fixed-first는 **Tier 0**에서 푼다. 고정 로봇 K의 경로는 **그대로**이고, 대신 R이 한 스텝 늦게(t=5 → 6) 도착한다 — **양날의 검이 코드로 드러나는 예**. |
| `FixedFirstPlansRescuedAgentAfterTheAgentItBlocked` | 앞 순서 K가 W의 길을 막는 (b) 상황. 원래 방식은 **완전히 실패**하고, fixed-first는 K를 W 뒤에 계획해 **Tier 1에서 성공**한다(K가 막다른 칸으로 비켰다가 돌아옴). |

## 12.2 벤치마크에 추가한 측정값

| 컬럼 | 뜻 |
|---|---|
| `initial_soc` | 초기 계획의 **경로 비용 합**(모든 로봇의 도착 시각 합). "추가 비용" = 재계획 결과 − 이 값 |
| `*_soc` | 전체 재계획 / 선택적 재계획 결과의 경로 비용 합 |
| `*_changed` | `current_time` 이후 움직임이 초기 경로와 **달라진 로봇 수**. 다시 탐색했지만 같은 길이 나온 로봇은 세지 않는다 |
| `selective_replanned` | 실제로 다시 탐색된 로봇 수 |
| `selective_conflicts` | 결과 경로의 충돌 수(검증용, 항상 0이어야 함) |
| `--order priority\|fixed-first` | 선택적 재계획의 등록 순서. 시나리오 생성과 무관해서 같은 시나리오로 비교된다 |

도착 시각은 "마지막으로 목적지에 들어온 시각"으로 센다. 이미 도착한 로봇의 경로를 이어붙이면
끝에 목적지 대기 칸이 붙는데, 이걸 비용으로 세지 않기 위해서다.

결과 파일: `tools/results/order_{priority,fixedfirst}_t{1,5}.csv`(기본),
`tools/results/order_large_{priority,fixedfirst}_t{1,5}.csv`(대규모). 두 방식의 파일에서
시나리오(초기 계획, 전체 재계획 결과)가 **완전히 같음**을 확인했다.

## 12.5 양날의 검 — 공정하게 비교하기

위 표의 평균은 방법마다 성공한 시나리오가 달라서(fixed-first가 더 어려운 것까지 풂) 직접 비교에
한계가 있다. 그래서 **두 방법 모두 안전망 없이 성공한 시나리오만** 골라 한 개씩 짝지어 비교했다.

| 설정 | 비교한 시나리오 | 추가 비용 평균 (priority → fixed-first) | fixed-first 비용이 더 큼 / 같음 / 더 작음 | 최대 증가 |
|---|---|---|---|---|
| 기본, Tier 1 | 356 | 3.52 → 3.09 | 12 / 321 / 23 | +21 |
| 대규모, Tier 1 | 207 | 5.30 → 2.94 | 10 / 164 / 33 | +24 |
| 대규모, Tier 5 | 286 | 11.47 → 4.32 | 18 / 178 / 90 | +24 |

바뀐 로봇 수는 fixed-first가 **더 많은 경우가 거의 없다**(1 / 1 / 0개).

### 해석

- **양날의 검은 실제로 있다.** 예: 기본 open 40대 trial 40에서 priority는 Tier 1로 낮은 로봇을
  비키게 해 비용이 오히려 7 줄었는데, fixed-first는 Tier 0에서 W 혼자 돌아가게 해 비용이 14
  늘었다(차이 +21).
- **그래도 평균적으로는 fixed-first가 더 싸다(추정 해석).** priority에서 구조 로봇을 불러오면
  그 로봇도 경로가 바뀌고 돌아가야 한다. 숨은 충돌 때문에 여러 대를 부르면 그 비용이 쌓인다.
  fixed-first는 대부분 W 한 대의 우회로 끝난다.
- 극단적인 예: 대규모 corridor 200대 trial 48은 priority와 전체 재계획 모두 **실패**했고,
  fixed-first는 로봇 5대만 바꿔 풀었지만 추가 비용이 **178**이었다. "풀긴 풀었지만 비싼" 경우다.

## 12.6 남은 문제

1. **원인 판정이 거칠다(10장 문제 3, 11장 아이디어 3).** 대규모 corridor 200대 trial 43에서
   fixed-first가 Tier 1로 가며 **194대**를 불러왔다(추가 비용 373). A\*가 헤매며 한 번이라도
   막힌 칸의 주인을 전부 부르기 때문이다.
2. **A\* 실패가 느리다.** 기본 corridor 20대 trial 36에서 fixed-first가 281 ms 걸렸다
   (priority는 2 ms). Tier 0의 A\*가 실패하며 시공간 전체를 다 뒤진 것으로 보인다(추정 — 따로
   재지 않았다). 아이디어 3의 "지도+장애물만으로 갈 수 있나?" 검사가 이런 헛탐색을 줄인다.
3. **(b)는 예측대로 유일한 확장 원인이 됐지만, 드물다.** 등록 거절이 원리상 없어졌으므로 Tier가
   올라가는 이유는 A\* 실패뿐이다. 그 수는 대규모 400개 중 Tier 1 7개 + 안전망 3개였다.
4. **비교 기준의 한계.** 전체 재계획도 `agents` 순서 한 번짜리 PP라서, fixed-first가 전체
   재계획보다 많이 푸는 것이 "선택적 재계획이 원래 더 강하다"는 뜻은 아니다. 논문에서는 이 점을
   밝혀야 한다(10장 문제 4).
